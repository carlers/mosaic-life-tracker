# Mosaic full E2EE and trusted-device enrollment — implementation blueprint

**Plan date:** 2026-11-19. **Parent:** [#1662](https://github.com/carlers/mosaic-life-tracker/issues/1662); security audit [#936](https://github.com/carlers/mosaic-life-tracker/issues/936), release boundary [#889](https://github.com/carlers/mosaic-life-tracker/issues/889), client compatibility [#914](https://github.com/carlers/mosaic-life-tracker/issues/914), 2FA/MFA [#1658](https://github.com/carlers/mosaic-life-tracker/issues/1658). **Planning only, not deployment authorization.**

## 0. Agreed goal, constraints and source snapshot

**Owner-selected product experience (supersedes the older PIN-vault plan):**
1. Enable client-side E2EE for all protected Mosaic *private user contents*, including personal tasks, categories, Diary, Bucket List, protected settings, attachments, private social messages and authorized shared content. Authenticated users/authorized recipients decrypt on their own enrolled endpoints. Publicly published data, necessary routing/operational metadata and login credentials cannot honestly be promised confidential from the operator; classify and disclose them explicitly.
2. First device creates a cryptographically random 256-bit account root and a **separate independent 256-bit emergency recovery key**. User backs up the long recovery secret, preferably in a password manager plus optional offline secure backup. It is not the Appwrite login password, an MFA code or a six-digit PIN.
3. Normal usage on an enrolled, suitably protected device automatically unwraps its locally held root wrapper; the recovery key is not requested at every sign-in. Unknown/new devices initially use the saved high-entropy key. Losing all enrolled devices *and* this key may permanently destroy the ability to decrypt previous data; account password reset does not circumvent E2EE.
4. Once comprehensive E2EE is operating on disposable Scratch, add optional **trusted-device approval**: new authenticated device requests enrollment; existing authenticated/unlocked device verifies the request and encrypts the root only to the new device's authenticated ephemeral public key. No remote short-PIN vault, no direct server decryption and no new paid infrastructure. A saved emergency key always remains the fallback.
5. **Both encryption and enrollment must pass the full Scratch and relevant real-device gates before requesting any main/Production promotion.** Preview → explicitly approved dev (Scratch-backed) → separately explicitly approved main/Production remains mandatory. **No Production changes or v1.0 authorization** is implied. Deployment cannot be declared secure after only unit tests.
6. Reuse Appwrite, React/Vite PWA, owner-scoped RxDB replication, existing Function/CAS, Vercel, schema migrations, CI and repository issue/PR workflow. Avoid replacing the backend and avoid introducing always-on independent recovery realms, additional billable HSMs or routine manual dashboard operations. Biometric, passkey and six-digit PIN recovery experiments are **deferred**.

## 1. Security promise and exclusions (required before implementation)

**Positive guarantee to test:** A copied Appwrite database/Storage snapshot, ordinary backend logs, DR backup and any non-compromised honest server process contain **only ciphertext for classified protected contents**; Appwrite authorization never reconstructs a client root; neither the account login password nor MFA completion alone is sufficient to decrypt previously encrypted content on a genuinely new device. Recipients can decrypt only content for which they hold a recipient/room/share key.

**Important limits:** An operator who changes the delivered PWA JavaScript or compromises the browser origin can capture keys/plaintext *when a client unlocks*; a compromised or unlocked endpoint can read its content; local device storage is not automatically a hardware secure enclave; traffic, lengths, timestamps, owner/recipient IDs, account identities and declared scheduling metadata may remain server-visible. Old plaintext backups/logs generated **before** E2EE activation may remain readable until their retention/purge lifecycle ends, and content already shared publicly cannot be retroactively hidden. E2EE is **not** a promise that every server field is encrypted or that the app is immune to its own malicious code-delivery channel. Publish these limits plainly and review with #936.

**Metadata default proposal:** Keep only immutable owner/row identifiers, ACL/visibility routing, revisions, tombstones, delivery/created timestamps, minimal event/day/reminder timestamps when required for alerts, and account/security state in server-visible metadata; encrypt titles, text, categories, private preferences, content URLs, diary quotes, image bytes/metadata, rich previews, reactions that reveal content, and identifiers that expose private semantics. Server-run reminder messages must use generic text unless delivered to an unlocked device for local assembly. An individual choice to mark content **public** deliberately opts into publication; it is not E2EE against arbitrary viewers/operators. For followers/shared recipients use recipient-key envelopes and explicit share authorization. Revisit every field and server Function under the manifest before declaring compliance.

**Explicit initial local-at-rest limitation:** E2EE of remote sync does not automatically encrypt existing local RxDB/Dexie plaintext. Preserve offline-first UX; clear identity-specific keys and decrypted caches on logout/account switch and ensure no cross-user display. Evaluate encryption of persisted local cache independently against iOS/PWA constraints; until proven, document that an attacker with the unlocked browser profile/device may read cached content even without an Appwrite session. A visually locked UI must not be claimed as a cryptographic local lock.

## 2. Concrete cryptographic and data contracts

### 2.1 Reuse the pilot; do not invent a cipher

- Isolate reviewed module boundaries: e2ee/crypto (Web Crypto), e2ee/keyring (root lifecycle), e2ee/recordCodec (versioned AEAD), e2ee/domainRegistry (privacy classification), e2ee/replicationBridge (encrypted remote, typed decrypted domain models), e2ee/migrations (resume/verify), e2ee/deviceEnrollment (later), and e2ee/sharing (separate reviewed primitives). Proposed file roles, **not files already created**.
- Generate a random 32-byte account root with secure RNG. Derive purpose/epoch/domain-separated keys via HKDF with independently versioned context, or generate per-record data keys where independent rotation/sharing needs them. Do not derive root or media keys from the Appwrite password or a short PIN.
- AES-256-GCM via browser Web Crypto for encrypted payloads/root wrappers as in pilot; fresh unpredictable **unique 96-bit nonce for each encryption under the same key**; authentication tag; canonical bounded serialization; AAD bound to project, immutable owner, collection/domain, logical row ID, client-controlled revision/operation nonce, envelope version, key ID and share scope. **Do not bind AAD to an Appwrite-generated timestamp that changes after encryption**. Explicit size limits and maximum nonce-use policy; corrupted/replayed/mismatched-owner payload fails closed with no plaintext fallback.
- Versioned envelopes: formatVersion, algorithm, keyId/keyEpoch, clientRevision, iv, ciphertext/tag, authenticated context, and nonsecret server indexing metadata. Envelope layout and migration/version vectors are tested across supported clients. Preserve read-only older envelope decoder until key migration and client support sunsets; never let older versions be used to write plaintext.
- Root wrapping independent of content: root encrypted once under independent 256-bit recovery key for remote backup; separate local device-bound wrapping key and envelope for each enrolled device. Changing backup/recovery wrapper must **not** reencrypt every task. If root itself is compromised, plan full content and sharing-key rotation, not merely rewrap.
- Browser nonextractable CryptoKeys persisted locally are *not* proof of secure hardware or OS-bound access. Normal resumed-browser sessions can use a remembered device wrapper; on storage eviction/offline sandbox failures show the recovery screen without destroying server ciphertext. No secrets in localStorage, logs, Analytics, third-party scripts, URL, browser screenshots, emails or push.
- Choose a modern **reviewed public-key scheme** for device-to-device enrollment and recipient sharing: IETF HPKE RFC 9180 is the protocol target; consider the open-source WebCrypto-based hpke-js/@hpke/core implementation after license, audit, browser and dependency review. For long-lived chat sessions, choose a maintained browser-compatible **Signal-like or MLS (RFC 9420) group messaging implementation** and validate actual browser/PWA support; do not hand-roll a ratchet or falsely claim forward secrecy with simple static HPKE envelopes. Messaging library selection is a real first-stage technical gate; raw libsignal TypeScript bindings' browser compatibility is **not yet validated**.

### 2.2 Backend schema and old-client cutover

**Default target:** an **additive versioned ciphertext contract alongside legacy tables** rather than putting opaque ciphertext into required existing plaintext columns (e.g., tasks.title, categories.name, bucket_list_items.title, settings.value). Evaluate a limited number of owner-encrypted domain tables with one shared codec/metadata shape, plus separately indexed/routed encrypted messages and authenticated key-envelope/device records. This minimizes required legacy field hacks; choose exact table partition/index topology by a focused benchmark and server-function query audit before first migration. Every new column/bucket/Function is declared in infrastructure/mosaic-backend.mjs and ordered scripts/appwrite-migrate.mjs, with strict checked expected schema; no dashboard-only schema edits.

Expected logical records/contracts:
- **Account E2EE state:** immutable owner, state/version, current key epoch, cutover phase, migration checkpoint and effective minimum encrypted client contract; only the client can authorize transitions that need root. Server marker is not a decryption key.
- **Recovery and device envelopes:** owner, key/epoch, versioned encrypted root, enrolled-device public metadata, created/revoked status. Never store decrypted root/PIN or weak verifier. Device enrollment records added in later phase.
- **Encrypted owner records:** owner/domain/opaque row ID, client revision, envelope, metadata required for owner polling/CAS, tombstone, visibility/scheduling fields only if reviewed. Preserve key reference and owner-scoped conflict detection/idempotency.
- **Encrypted share/member/recipient records:** stable share/room/thread identifiers, recipient identity, authenticated encrypted scope key per authorized device/participant, epoch/grant/revocation, allowed action state. Server ACL remains necessary in addition to crypto.
- **Encrypted attachments:** encrypted bytes in dedicated/restricted Storage path/bucket or equivalent robust envelope, authenticated file manifest, opaque IDs, hashes only where not leaking plaintext semantics, resumable content upload and cleanup.

**CRITICAL blocking issue before claiming E2EE:** Older installed clients can currently bypass the message-action Function and **directly create/update legacy Appwrite rows or upload unencrypted file bytes**. An e2ee_required Boolean or a client-only feature flag is *not* sufficient. Plan a two-step guard:
1. Route *all* protected writers through a server-owned validated write/CAS boundary; carefully stage/retire legacy user direct row create/update/delete grants and legacy direct plaintext Storage upload grants (including existing row permissions). Do not activate a global ACL change on a shared Scratch or Production project while breaking other supported users; use disposable isolated fixtures, compatibility gates and reviewed transition policy.
2. Activate an owner/domain **cryptographic write floor** only after encrypted clients are ready, blocking **every** legacy route: TablesDB create/update, Function create/CAS, friendship/calendar shared writes, Chat send/replies, owner media files, bypass/maintenance Function, offline queued writes, imports, backups, restore, service-worker obsolete clients, and Admin/DR replay. Reject wrong ciphertext envelope/version, account key mismatch and plaintext downgrade. Even valid-looking ciphertext from a malicious client does not prove its content was encrypted; distinguish honest-client prevention from malicious-JavaScript threat.

**Account state machine:** UNENROLLED → RECOVERY_KEY_BACKED_UP → MIGRATING (bounded resumable checkpoints) → ENCRYPTED (irreversible floor) with separate DEVICE_RECOVERY_REQUIRED, DEVICE_ENROLLMENT_PENDING, REKEYING, and ERROR_NEEDS_RETRY states. Never call an account ENCRYPTED until 100% of defined protected records/files are verified as ciphertext, no pending plaintext outbound queue exists, and legacy write paths are fenced. Interrupted migration must resume without silently losing, duplicating or rewriting newer records. Rollback rolls forward encrypted data; never silently downgrade to plaintext.

**Legacy residuals:** After migration, verified plaintext column/old Storage object cleanup and retention/DR cleanup must follow an approved policy. No claim that old plaintext snapshots were retroactively protected. Keep explicit recovery/failed-migration rollback without a plaintext backdoor.

## 3. Executable sequence: five gated work packages

### M0 — Refresh baseline and adopt architecture (first, shortest path)
**Branch:** new scoped task branch from current live dev (do **not** blindly merge stale pilot PR #2037; selectively adapt reviewed files/tests after diff/rebase). Verify root/child AGENTS, docs index, live issue/PR/CI; inspect actual Scratch state/Function/permissions via read-only tools, current app schema/Storage and old-client matrix. Inventory every network write, Function and data field, classify using domainRegistry manifest. Decide envelope-table topology and algorithm/recipient protocol after focused compatibility/performance security check. Document PWA cache and code-delivery limits. Tie issue #1662 and #936. **Exit evidence:** field/route matrix with no unclassified sensitive fields, exact backed-up current branch SHA, Scratch parity report or explicit blocker, reviewed crypto primitives and supported browser matrix.

### M1 — Key lifecycle and synthetic/private Diary integration
Port pilot's random root, recovery-key wrapper, device wrapper, AEAD/AAD negative tests and independently verified JWT owner/MFA checks into a reusable typed keyring/codec; no PIN. Validate fully authenticated enrolled/unrecognized device transitions, secure setup + explicit recovery-code backup acknowledgement, reset/loss/rotation and logout/account switch. Add root-envelope, account-state and minimum ciphertext schema in Git-owned additive migrations/Function contracts; use only synthetic, opt-in, default-off allowlisted Scratch account. **Exit:** no Appwrite/root/log/plaintext leak from synthetic Diary, correct wrong-key/tamper/wrong-owner behavior, remembered-device offline access, new-device recovery with copied backup key, unknown-client versions fail closed, real browser support verified.

### M2 — Full personal-domain encryption + backend closure and migration
Implement one shared encryption adapter for tasks, categories, Diary, bucket lists, private settings, routines and related task relationships; limit UI changes to onboarding and failure states. Add encrypted file upload/download, manifest, local cache/logout cleanup, search/client-only post-decrypt, generic alerts and export/import compatibility. Move protected sync paths behind validated Function/CAS envelope writes and close legacy direct writers on appropriately isolated Scratch, including old PWAs, imported ZIPs and media. Build resumable, idempotent owner-local migration of existing plaintext rows and files: snapshot counts/checkpoints, CAS against live updates, verify each ciphertext by decrypting on the authorized client before tombstoning old rows; dry-run, resume and rollback without a plaintext downgrade. **Exit:** migration exercises no/large/offline/two-device records, excludes no private content, no client/Appwrite/backend route can transmit legacy private plaintext after write floor, no lost unsynced edits, DR/erasure/restore match the new manifest.

### M3 — Complete social/content E2EE (no proprietary protocol invention)
Add authenticated recipient public-key/device identity, account key/epoch identity verification, recipient envelope exchange and revocation for shared tasks, friend calendar views, Diary quotes, controlled visibility and media. Select reviewed browser-compatible chat session protocol, handle membership/device changes and offline delivery, edit/reply/unsend/duplicate/self+peer message copies, replay, attachment encryption and notifications. Publish explicit consequences: newly revoked recipients cannot decrypt *future* epochs, but already seen/plaintext/cache copies cannot be recalled. Public/user-published content is not secretly recoverable only by the user; document it. **Exit:** all current private/social flows work across multiple accounts/devices with wrong-recipient, blocked-friend, public/followers/private, server-authorized mutation and recipient-revocation tests; no private text enters Function responses, logs, push or offline queues.

### M4 — Trusted-device enrollment and final Scratch release-candidate validation
After M1–M3 encrypted functionality passes, implement an optional Bitwarden-style second-device approval, independent of account login and MFA. New device signs in/finishes MFA, creates ephemeral asymmetric key pair and short-lived request ID; relay only public key and encrypted response through owner-bound Scratch Function/table; existing unlocked device must show device/request and compare a **short authentication fingerprint** through an independent human check before encrypting root to the new ephemeral key (review RFC 9180 HPKE + browser implementation); new device unwraps and generates its own local device wrapper. Include approval expiry, denial, replay, identity substitution, wrong owner, double approval, lost/removed device, unauthorized server relays, key rotations and recovery-key fallback. Explicitly prevent accidental QR-based transmission of the **recovery secret itself**. Provide device list/revoke UI with honest revocation semantics (cannot retroactively erase already held root; if compromised, rotate content root/epochs appropriately). **Exit:** full cross-device test matrix passes and the recovery secret is only needed when no trusted approving device exists, not at ordinary startup.

### M5 — Comprehensive Scratch acceptance and separately approved staged publication
Keep all E2EE development and device enrollment on disposable Scratch data and versioned Preview branches until complete. Perform canonical CI, schema drift, browser-contract and handler tests; live Scratch Function deployment/real Appwrite ACL and old-PWA rehearsal; hostile-client simulation; real Android/iOS installed PWA handling; tests for large data, slow networks, background/offline/multi-tab, legacy queued writes, storage eviction, incomplete migrations, device loss, duplicate re-enrollment, compromised recipient, paid-quota guard, DR restore and deleted-account nonresurrection. Complete independent crypto/security review commensurate with the scope before marketing zero-knowledge/operator-blind E2EE. Produce exact-SHA test evidence and disclosure copy in #936/#889. After owner accepts Preview, eligible promotion to dev requires explicit authorization; **main/Production migration/release requires separate, later, explicit authorization and a fresh exact-main compatibility+backup/DR preflight**. Treat secure rollout as a separate production migration plan; never repoint official main as a side effect of Scratch testing. **Exit:** signed-off go/no-go report including all remaining risks and manual acceptance, no failed mandatory gate.

**The M0–M5 numbers are work packages, not dates or guaranteed one-PR deployments.** Split into scoped issues and branches; allow multiple Preview acceptance cycles for the whole feature. Individual phases may become parallel tasks only when key contracts are stable. Budget and CI cost must be checked before provisioning. No attempt to guarantee absolute absence of security defects.

## 8. Independent readiness hardening and execution handoff (2026-11-19)

This audit **adds mandatory checks** to M0–M5; it is a planning update, not proof that cryptography, schema or backend controls are deployed.

### 8.1 First-device, recovery and local key state (#2083)

- **Atomic bootstrap:** Two devices or tabs enrolling simultaneously must not establish conflicting roots. Enforce a single owner-scoped compare-and-create root/epoch registration. Losing initiators recover the accepted encrypted root, never publish independently encrypted data. Test retry-after-timeout, MFA-pending, failed first envelope upload and race across accounts.
- **Verifiable emergency backup:** A uniformly random 256-bit recovery key needs copyable/pasteable user-safe encoding with checksum/error detection and clear distinction from the Appwrite account password and MFA recovery codes. Verify a saved key locally through a real unwrap before declaring backup complete. Persist the root/recovery envelope durably before allowing protected sync writes; resume aborted onboarding without silent key reset. Simulate device loss, IndexedDB eviction, forgotten key and password reset.
- **Rotation transaction:** Recovery-key replacement rewraps the same root with a freshly random secret, preserving ciphertext. Require verified durable new envelope plus epoch/CAS before retiring the old wrapper; do not strand clients or claim a local-only update succeeded. Root/key *compromise* demands root/content/share rekey and coordinated multi-device recovery; changing a wrapper alone is insufficient.
- **Local scope and honest claims:** Nonextractable IndexedDB CryptoKeys are not hardware-backed evidence, and same-origin JavaScript can still use them. A remembered enrolled device may automatically decrypt after normal authentication, but a new unrecognized device cannot recover from password/MFA alone. Account auth, MFA, key lock, offline identity and plaintext RxDB/Dexie cache are distinct. Test logout/account switching, locked background operations, concurrent tabs, browser cache eviction and PWA restarts. Never label a UI-only lock as cryptographic local-at-rest protection.

### 8.2 Writer inventory, migration and privacy (#2084)

- **List every sink:** Audit direct owner TablesDB create/update, owner-row-create/CAS Functions, all legacy and reserved/offline Storage createFile paths, chat/shared Functions, outboxes, imports/exports, backups/restores, notifications, service workers, server search/preview, telemetry and active voice/AI/MCP/integration previews. New protected outbound fields and sinks must be classified in the CI privacy manifest; no unknown sink silently defaults to plaintext.
- **Actual server-enforced floor:** Moving normal code to a Function cannot stop an old authenticated PWA with historical direct Table or Storage grants. Close table and existing per-row ACL/bucket permission bypasses, not just Function branches. Test raw direct requests and replayed old versions. Reject all protected plaintext writes after account cutover, provide an update-required/read-only state preserving locally queued edits, and never make plaintext fallback part of rollback.
- **Idempotent migration:** Inventory owner rows/files and outstanding local edits. Each opaque logical row/file identity, revision, tombstone and key epoch needs a deterministic checkpoint, CAS/concurrency protection, authorized decrypt/readback verification before old authoritative rows are retired, and retryable resume after interruption. Test two-device conflicting edits, old PWA reconnect, duplicate upload, offline queue, account erasure and restore nonresurrection. Existing historical plaintext DR snapshots remain operator-readable under DR escrow until expiry; encryption cannot retroactively conceal them.
- **Leakage inventory:** Classify task/category IDs, dates, names, tags, ordering, settings keys/values, photo metadata/EXIF/thumbnails, quote/reply content, push/notification text, social graph, public content, analytics and log breadcrumbs, and file/request lengths. Do not mark user-published plaintext or operational metadata as fully secret. Inspect canary text in TablesDB, Storage, Functions, errors, responses, retries, notifications, backups, caches and permitted external integrations.
- **Performance and quotas:** Benchmark payload, media chunks, Appwrite limits, migration cost, browser CPU/memory/IndexedDB quota, installed PWA lifecycle and CI bundle size before fixing table topology. No paid infrastructure or Production mutation implied.

### 8.3 Social identity, protocol and rollback (#2085)

- **Authenticated peer keys:** Merely asking the server for a public key is not independent verification. Define account/device identity keys, key-change warnings, sender pinning, user-verifiable out-of-band fingerprint/safety-number checks, malicious server key substitution and lost-device behavior. Until verified, label the exact trust level honestly.
- **Only scoped sharing keys:** Never give recipients the owner's account root or emergency recovery key. Wrap per-share/conversation epoch keys to authorized recipient devices. Cover grant/revoke, member changes, edits, offline recipients, former-device access and multiple device copies. Revocation prevents access to *future* epochs only; past decrypted copies cannot be erased remotely.
- **Messenger dependency is a real selection gate:** HPKE (RFC 9180) is suitable for reviewed key transport, not a substitute for a maintained double ratchet/MLS long-lived session. Signal's official published JavaScript package binds native desktop Node libraries and has no established general browser/PWA support. OpenMLS includes a WASM build target, but the selected adapter still needs real browser/iOS/Android compatibility, persistence, membership, protocol vectors, dependency/license and independent security assessment. Do not invent a custom ratchet or claim forward secrecy until evidenced. If no safe browser candidate passes, stop the full-chat E2EE release gate and report scope honestly.
- **Replay and rollback bounds:** Authenticate owner, domain, row, message, revision and epoch with AEAD and enforced monotonic state/CAS. Test rollbacks and key substitutions. A new device with no independent trusted checkpoint may be unable to detect an all-state rollback by a malicious service; do not promise perfect malicious-server rollback detection.

### 8.4 Trusted-device enrollment and full validation (#2086–#2087)

- **Out-of-band authentication:** New device must first sign in/complete MFA, then issue short-lived one-time owner-bound public-key enrollment request. An existing unlocked device verifies the *new device's own* fingerprint by independent on-screen comparison or local scan before HPKE-encrypting the root to that ephemeral key. Same-relay labels alone do not prove the public key. Reject swapped keys, wrong account, races, expiry, replay, denied and MFA-incomplete requests. The recovery secret never appears in relay, URL, push, QR, logs or telemetry.
- **Device removal != cryptographic erasure:** An already compromised device may retain an older root or plaintext. Expose revocation limits and a tested full content/share key rotation path for compromised devices, including delayed/offline recipients.
- **Independent acceptance:** Exact-SHA canonical CI, live Scratch manifest/Function/ACL/origin, negative privacy canaries, old-PWA/queued-write rehearsal, real Android/iOS installed PWA, migration/DR/erasure recovery, and independent cryptographic/protocol review are required before a broad E2EE security claim. Explicitly disclose malicious delivered JavaScript, local plaintext-cache access, metadata and old snapshot retention. Neither tests nor reviews prove literal zero defects.
