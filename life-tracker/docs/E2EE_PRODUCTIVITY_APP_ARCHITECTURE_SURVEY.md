# E2EE productivity-app precedents and low-maintenance Mosaic architecture

**Research date:** 2026-11-19. **Issue:** [#1662](https://github.com/carlers/mosaic-life-tracker/issues/1662). **Scope:** competitor architecture, recovery, E2EE feature implications, costs/operability, and integration planning. **Source snapshot:** Mosaic live dev c984ff30ee004d7ee7a68b3807de42e4cc4c3829. **Constraint:** $0 new infrastructure spend; defer biometric and passkey features; keep user-chosen six-digit PIN recovery as a *desired* feature, not permission to deploy an unverified PIN vault. No application, backend, Production or real user-data changes made.

## Executive decision

**Recommendation:** Adopt the low-maintenance, established *client-side encrypted-data-key / wrapped-key* model used by Joplin, Standard Notes, Notesnook and Etebase, layered over the current Appwrite + RxDB + Vercel stack. Do **not** substitute a completely new synced backend (Etebase, Anytype/AnySync or Joplin Server) for Appwrite as the default path. Do **not** make an unproven Juicebox production service a prerequisite for implementing E2EE. Use the existing high-entropy emergency recovery-key method as the cryptographic fallback while separately researching user-friendly six-digit PIN-only recovery with a truly validated recovery service. Do not market a server-admin-accessible key release path as administrator-blind E2EE. This is a proposed research decision, not an implementation authorization.

**Core learning:** E2EE is generally encrypted by default and transparent during routine use; forgotten account credentials/key material may cause permanent data loss. The six-digit PIN is not an industry-standard E2EE prerequisite. Some apps additionally offer a **device-local app passcode**; this is not a universal lost-device recovery PIN and does not require a remotely hosted HSM vault. Industry apps finance hosting and support using free/paid subscriptions, donations or users' own infrastructure. Public pricing is evidence of what users pay, **not** of the companies' actual security/hardware operating costs; those internal costs were not disclosed in sources reviewed.

## Why "use Standard Notes' password scheme" is not directly safe in Mosaic

The current production-like Mosaic client calls the Appwrite password-session operation with the user's email and **ordinary account password**, shown by live source in life-tracker/src/hooks/AuthProvider.tsx. That transport delivers the account password to the Appwrite authentication service, unlike Etebase's published proof-of-possession protocol or Standard Notes' distinct derived server password. Reusing that **same** password as the only root-key derivation input would permit a sufficiently privileged Appwrite operator to observe the credential during authentication and potentially reconstruct user encryption keys. That would weaken the intended "backend never learns encryption secrets" guarantee.

**Safer scoped choice with existing Appwrite:** keep Appwrite account authentication and optional MFA unchanged; generate a client-side **random 256-bit account root**, independently protect its wrappers with a **high-entropy, user-held recovery key** and per-device keys; never derive cloud decryptability solely from the Appwrite login password or an offline-verifiable six-digit PIN. Cross-device recovery via a six-digit PIN may be introduced **only** after a suitable Juicebox/guardians/HSM-grade service demonstrably protects key release. Etebase can use a login password cryptographically because **its login protocol differs from Appwrite's**; do not transplant the UX alone.

This is not proof that a malicious operator cannot ever compromise a web E2EE app: same-origin JS replacement or XSS can capture live plaintext/keys. EteSync's own FAQ explicitly calls out that browser-delivered encryption code can be modified by the server. This threat must be in the published security statement for a browser-only PWA.

## Proposed Mosaic design: reuse established primitives, keep Appwrite

**Data flow:** UI and local app state -> reviewed encrypted-storage/sync adapter -> ciphertext Appwrite tables/Storage -> ciphertext backup/DR -> other authenticated client decrypts locally. The server remains authoritative over account identities/ACLs, permitted metadata, mutation ordering, timestamps and tombstones, not private contents.

1. **Key hierarchy:** Random root secret with versioned root envelope; independently random domain/subcollection or per-record data-encryption keys, wrapped under an account-level key; separate per-recipient sharing keys for shared tasks/message conversations. Never store unwrapped root on server or logs. Use standard AEAD (native Web Crypto AES-256-GCM/HKDF where suitable, or vetted libsodium XChaCha20-Poly1305 if required), secure randomness, fresh nonce per key, AAD-bound owner/row/revision/version; **no novel crypto algorithm**. Choose one primitive set after dependency/interop review; current isolated private-Diary crypto is useful starting evidence, not ready for every domain.
2. **Key wrappers separate from content:** store algorithm / key epoch / cryptographic payload version and authenticated ciphertext; rewrap root/data-key envelopes on PIN/passphrase or recovery changes; avoid rewriting millions of content rows unless key material is compromised or the data format itself changes. Joplin and Notesnook explicitly support key rewrapping.
3. **Explicit privacy classes:** (a) encrypted private payload, (b) operational metadata visible to server, (c) intentionally shared/public data, (d) server security/audit data. Exempt fields need a written justification and accurate product disclosure. No blanket "all data encrypted" statement when task dates/status and participants remain visible.
4. **Local-first:** local RxDB may continue serving the UI, but ensure persisted plaintext caches, decrypted search indexes, thumbnails, push payloads, offline queue and old service-worker code do not bypass the intended locked/privacy state. A PWA has weaker key storage than a native OS keychain; choose strict documented boundaries instead of claiming native enclave equivalence.
5. **Backend versioning:** encrypted record has stable owner, row ID, deletion marker, sync revision, metadata schema, cipher version and key ID/epoch; private fields live in a versioned authenticated ciphertext document; client decodes before exposing to domain React components. Clients must fail closed on unsupported cipher versions or downgraded plaintext rows. Auth and row-security still apply to ciphertext.
6. **Sharing:** recipient public-key registration, authenticated key identity and share-specific wrapped key distribution; rotate forward keys for new content after revocation. Do not claim past ciphertext/previously received content can be recalled. Joplin shared notebook design and EteSync's revocation warnings show why message/task sharing needs a separate phase.
7. **Backup and deletion:** DR snapshots back up only encrypted payload plus necessary wrapped-key state, versioned manifest and user erasure markers. A backup without a usable root is unrecoverable; deleting a wrapped key is not identical to erasing every server/recipient copy. Preserve deletion/DR contracts.
8. **PIN recovery boundary:** E2EE itself needs no remote PIN vault; six-digit PIN recovery is an optional key-escrow/release adapter with its *own security and availability review*. It must never switch to a server-side decryptable key or plaintext fallback without a user-visible, specifically authorized reduction in privacy guarantees.

### Preliminary field ownership for current Mosaic sync contracts

Based on dev life-tracker/src/lib/syncMapping.ts and life-tracker/infrastructure/mosaic-backend.mjs. This is a planning classification, **not a complete field audit**:

| Domain | Encrypt by default on client | Candidate server-visible minimum / rationale | Feature consequences |
|---|---|---|---|
| Diary | entry content, private emoji, photo bytes, excerpts, quote content | immutable owner, row identity, deletion, possible day metadata only if required | Diary previews, quotes, sharing and offline images need encrypted-domain handling |
| Tasks | title, memo, image, private tags, category name/label | dates, completion/status, reminder timestamp only if server reminders truly need them | Calendar view can continue using locally decrypted content; server tasks cannot search/quote plain content |
| Categories / routines | private names, sensitive labels/settings | IDs, order, visibility semantics only if necessary for ACL | Cross-device category actions and shares need versioned private payloads |
| Messages / shared tasks | message/reply bodies, task/diary quoted text, attachments | sender/recipient/thread routing identifiers, delivery time/status | Separate session/recipient keys, rekey on membership changes, ciphertext quoting, no plaintext Function previews |
| Bucket list | titles/descriptions/media | owner, item IDs, tombstones, minimal ordering | Client search and grouping after local decryption |
| Photos and files | all protected original bytes, thumbnails, filenames/exif if sensitive | random file ID, length and content type only where unavoidable | Client upload/decrypt, cache purge and account erasure |
| Settings | sensitive preference values and user-controlled private text only | auth, capability and policy values needed by backend/security | Avoid encrypting settings required before acquiring a key or by server gating |
| Friends/social | private shared content per recipient scope | authenticated identity, ACL, delivery routing | Do not confuse server read permission with recipient crypto eligibility |

**Two honest choices** for calendar privacy: (1) encrypt contents and leave limited scheduling metadata visible, modeled on Proton Calendar/Lunatask; or (2) encrypt dates too, accepting server-side reminders and indexing loss or redesign. Any "everything is encrypted" claim would be inaccurate for choice (1). The user must choose privacy/functionality scope before full release, not during unreviewed migration.

## Keeping development nearly unchanged: exact workflow plan

### Stable abstractions, not pervasive crypto edits

- Add a **central codec** at the sync boundary (encode/decode/encrypted row type), plus an explicit versioned **encryption-domain manifest**. Existing page/domain models can continue using typed decrypted objects after the authorized local key has been unlocked. Avoid scattering encryption calls throughout every component.
- Keep backward-compatible encrypted envelopes and schema versions: storage changes to ordinary private task fields generally change client payload schemas or codecs without adding new Appwrite columns. Backend shape changes are required when adding truly new metadata/indexes, new ciphertext buckets, key-envelope records, new recipient records, or breaking encryption versions; these remain planned migrations.
- Use **lazy client-side payload migration** on read/write for new field versions where safe, plus guarded and resumable initial whole-account migration. Never silently re-encrypt or delete content when offline queued writes, unknown PWA clients, or missing keys exist.
- Make the **server enforce encrypted-only writes** for protected domains and reject unsupported/legacy plaintext writes after an explicitly staged closure. Do this before claiming end-to-end encryption. Historical service-worker/queued-write clients must be accounted for; a new frontend toggle is insufficient.
- Encrypt files **before Appwrite Storage upload** and version associated metadata. No server-side image transformation/indexing that needs plaintext unless explicit user consent to a separate weaker-privacy mode.

### CI/automation additions (should be repo-owned and run through normal GitHub PR / Preview)

| Change | Automated check |
|---|---|
| New/changed managed Appwrite field | Encryption manifest has classification and justification; privacy guard fails on missing/unknown private field |
| New/changed client codec or record | Cross-version encode/decode, key epoch, tamper/AAD, wrong owner, stale revision, failure-mode tests |
| Any protected network write | Assert no plaintext from the relevant domain reaches Appwrite requests, Function or DR; negative test aborted E2EE onboarding |
| New schema/backfill | Synthetic Scratch migration + idempotence, rollback/resume, compatibility test with supported pinned old PWAs |
| New shared/domain action | Recipient envelope integrity, cross-account negative tests and revoked-recipient state; never server-side "decrypt to do action" |
| Cipher or key rotation | Versioned wrappers / rewrap compatibility, old-key retention, recovery and interrupted migration tests |
| Release to Preview | Existing scoped focused verifier and full canonical CI, stable Preview/Scratch tests, synthetic account/device acceptance |
| dev / main promotion | Existing explicit owner approval gates; protected CI, exact SHA verification, and Production authorization unchanged |

**Routine UI changes** that do not affect encrypted models, backend contracts or key handling should continue normal task -> focused tests -> Preview -> owner approval -> dev -> separate production approval. No special manual console procedure per ordinary task or Diary field. **Security/crypto and schema changes** must trigger additional automated checks; true provider permission, migration, auth-provider and Production changes require their existing explicit approvals.

### Owner / agent responsibility and maintenance cost

**Agent-managed using connected tools:** live GitHub issue/branch/PR tracking; source/dependency changes; synthetic tests; CI and Vercel Preview inspections; Appwrite Scratch compatible migrations through existing connected Oracle operations if permitted and safely scoped; encrypted-domain manifests; documentation; status and rollback evidence. Existing release gates remain protected and cannot be silently bypassed.

**Owner involvement should be rare but not literally zero:** initial disclosure/privacy UX decision, initial personally saved recovery key, permission for destructive/key/Production operations, manual phone/PWA security usability testing and explicit Preview/dev/main sign-offs. Moving to independent Juicebox recovery realms would additionally require real realm operator onboarding, certificate/DNS/IAM ownership, backup/upgrade arrangements and ongoing security patch responsibility; those cannot honestly be promised "set once and never touch again" under current unmaintained Go realm and free-hosting constraints.

**Operational requirement:** CI should prevent dangerous changes rather than requiring routine manual checklists. Automatic upgrades to cryptographic dependencies, vault policy, PWA cipher versions, backend grants or global attempt counters must not silently ship without relevant test and approval evidence. Monitor dependency advisories, recovery-availability, failed account migrations and backfill completion without logging PINs or plaintext. DR drills and restoration of wrapped keys remain occasional activities.

## Specific industry warning: encrypted onboarding must never upload plaintext

[Super Productivity 2026 advisory GHSA-9v8x-68pf-p5x7](https://github.com/super-productivity/super-productivity/security/advisories/GHSA-9v8x-68pf-p5x7) documents a real E2EE setup bug in which task operations (and potentially provider credentials) uploaded in plaintext **before** encryption password creation. If setup was abandoned, the plaintext remained; affected clients were older than 18.13.1. Do not infer such a bug exists in Mosaic, but use it as a **must-fail negative CI regression**: initiating, cancelling or restarting enrollment must never allow a plaintext protected-domain network write after the encryption policy activates. A backend cryptographic write fence is more robust than relying on client prompt order.

## Prioritized roadmap and decision gates (not implementation permission)

- **R0 (design):** Confirm privacy coverage / server-visible metadata exception table; choose current Appwrite+RxDB reuse, root+wrapped data keys, high-entropy fallback; preserve six-digit PIN as desired separate recovery. Review connected Appwrite password flow and browser source-delivery threat. Document exactly which "administrator-blind" claims are and are not true.
- **R1 (isolate):** Use existing Scratch synthetic Diary pilot and extend one central encrypted sync mapping. Verify supported JS/PWA clients, local keys, no server plaintext, rewrap/recovery and older clients. No full-app claim.
- **R2 (migrate):** Server-side old-PWA write fence, staged current user migration with resumability, encrypted attachment backfill, backup/erasure/key envelope tests; then per-domain encrypted tasks/categories/bucket/diary/settings and gated messages/shared tasks. Prefer opt-in until migration safety is proven.
- **R3 (industrialize):** Manifest-driven compatibility gates and CI, client-side payload-version updates, refusal of plaintext downgrade; established Preview -> dev -> main release controls unchanged.
- **R4 (optional PIN recovery):** Reuse Juicebox only if a hardened, maintained, independently governed recovery service passes documented counter/rollback/admin/recoverability tests at an actually sustainable $0. Otherwise offer high-entropy recovery / trusted-device pairing. Do not ship an ordinary Appwrite rate limiter as a guarantee of PIN-only offline security.

### Decision matrix — do not conflate

| Plan | Extra infrastructure | New routine operations | Owner security semantics | Decision |
|---|---|---|---|---|
| Existing Appwrite + client E2EE + strong recovery key | **Likely $0** beyond already-running stack for reasonable scope; storage/bandwidth may still rise | Low after central codec and migration gates | Honest E2EE against passive backend data access; browser code-delivery and metadata caveats | **Preferred first production architecture to validate** |
| Local account-key passcode like Standard Notes | No required new server | Low if browser limitations accepted | Protects *local keys* on enrolled device; not six-digit standalone lost-device recovery | Optional separate UX, not a vault substitute |
| Etebase entire backend | Could self-host on existing capacity, not cost-free engineering | **High** — replaces sync/auth/ACL backend, conflicts with existing Appwrite contract | Strong established architecture, but oversized migration for current product | **Not recommended** |
| Juicebox three software realms, same Mosaic administrator | Could fit existing free resources | **High** — realms, service credentials, persistence, upgrades, DR, lockout | Does not genuinely prevent privileged Mosaic operator reaching recovery threshold | **Not equivalent to original threat model** |
| Juicebox truly independent realms | Unverified permanent $0 | **High/uncertain**, requires other administrators | Better operator separation conditional on availability/counter assumptions | Separate feasibility milestone |
| HSM/TEE protected recovery | No verified perpetual $0 offering | High/security-specific | Stronger counter assurances under attestation and audit | Deferred under budget |

**Bottom line:** The low-maintenance industry-established solution for Mosaic is **strong random client-side keys with versioned wrapped-key envelopes and explicit recoverability**, preserving Appwrite and the current repo-driven workflow. Competitors generally do **not** implement separate six-digit PIN-only recovery in their core productivity E2EE architecture. The desire for a separate Mosaic six-digit PIN is valid but should remain a separately gated convenience feature, not block E2EE or justify falsely reassuring claims. No product implementation, Preview, backend migration, new provider account or owner-paid resource has been created by this survey.
