# Zero-dollar six-digit E2EE recovery vault — feasibility survey

**Date:** 2026-11-18. **Controlling research for:** [#1662](https://github.com/carlers/mosaic-life-tracker/issues/1662). **Budget:** strictly **$0 additional infrastructure and ongoing spend**, no credit cards, free-trial-to-paid transitions or automatic charges. **Requested security:** arbitrary user-selected six-digit **Mosaic recovery PIN**, lost-all-devices key recovery after account password authentication, E2EE with no Appwrite/cloud/Mosaic operator plaintext access. **Fingerprint, device-PIN substitution and passkey UX deferred.**

**Verdict: NOT proven impossible.** Public research establishes credible no-specialized-hardware *threshold* PIN-protected secret recovery, and OCI supplies some genuinely Always Free HSM key storage. However, **no ready-to-run, production-validated, indefinitely $0, solo-operator-hosted PIN-only key vault that meets Mosaic's entire original operator-resistant threat model has been verified**. There is a crucial distinction between hardware cost, trust independence and protection from unlimited guessed PINs. This is a research conclusion, **not a formal impossibility proof** and **not approval to change backend or expose user data**. Reassess as offerings and protocol implementations change.

**Live source verification:** dev `c984ff30ee004d7ee7a68b3807de42e4cc4c3829` still uses plaintext ordinary task, category, diary, bucket list, settings and message sync (`life-tracker/src/lib/syncMapping.ts`). Isolated Scratch only has the tested separate encrypted private-Diary pilot on task branch `82995cd37041e61ac61feb5ca0ebd7a9250407d5`. This report modifies no runtime or Product source.

## Precise attacker and recovery requirements

| Level | Adversary | Security needed |
|---|---|---|
| A | External attacker copies only Appwrite rows, DB dump or backups | No downloadable, independently PIN-testable verifier or wrapped-root ciphertext; random root still secret |
| B | External attacker steals application API credentials, compromises Appwrite Function/OCI A1, rewrites stored records, or rolls back ordinary backups | Cannot extract recovery secret or obtain more than the authorized globally bounded PIN guesses |
| C | Privileged Mosaic operator controls OCI tenancy IAM, backend deployments and all recovery-service accounts | Even that operator cannot decrypt, change recovery code, reset attempts, replace vault code without independently detectible failure, or bypass admission |
| D | One cloud/host/realm operator is malicious | Other independent hardened/threshold trust domains prevent unilateral offline PIN enumeration |
| E | Browser code delivery itself is malicious (changed Vercel same-origin JavaScript or XSS) | Even a protected vault cannot prevent the malicious *client* from capturing entered PIN/plaintext once unlocked; requires an independently validated code-delivery trust solution outside ordinary PWA assumptions |

A six-digit PIN has **1,000,000 possibilities**. A permanent ten-attempt total caps uniformly random guessing at at most 10/1,000,000 = 0.001% before accounting for PIN choice biases and targeted guessing. A network API rate limiter or a database column is **not binding against an offline adversary** holding a self-verifying PIN-derived envelope. The server **cannot force a copied encrypted object to obey its rate limit**. Any design must either (i) keep an additional uncopyable or independently controlled secret off that database and enforce access, (ii) use multiple genuinely independent rate-limiting participants, or (iii) require another high-entropy user/OS secret. Account password/MFA admission is not a substitute for the encrypted key.

### Important NEW concrete find: Oracle Always Free HSM keys

- [OCI Always Free Vault allowance](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): 20 total HSM key versions and 150 secrets. [Oracle's Key Management FAQ](https://www.oracle.com/apac/security/cloud-security/key-management/faq/) says first 20 HSM key versions are free and management/crypto API requests are not billed per request. **Do not conflate shared multitenant Virtual Vault with paid single-tenant Private Vault, and do not allocate more versions than permitted.**
- [Oracle HSM master keys are nonexportable](https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Concepts/keyoverview.htm). [Oracle KMS decrypt](https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Tasks/usingkeys_topic-To_decrypt_data_by_using_your_Vault_master_encryption_key.htm) is callable by **authorized principals**. An administrator who can grant themselves decrypt permission or invoke the application's decrypt principal may bypass any ordinary separate six-digit PIN logic. Nonexportability protects the **master key**, not the recovered user key against authorized Decrypt.
- If Mosaic trusts OCI/IAM and its own server operators, this could provide **a real $0 database-theft-resistant vault**. If Mosaic promises *server/operator-blind E2EE*, it is **not** the final answer. Never label server-recoverable content operator-blind E2EE.
- Account-specific information not verified: existing free HSM key-version usage, IAM/root compartment permissions, region, current paid/Always Free tenancy status, allowed Vault product and client networking. Connected Mosaic Oracle bridge exposes Appwrite Scratch/Production, **not a read-only OCI Vault inventory**. Do not write/reconfigure infrastructure without separate approval and cost guard.

### Strong NEW free-software directions: Juicebox and Kintsugi

**Juicebox** is the closest reuse target with a published protocol and open-source SDK/server:
- [Juicebox SDK](https://github.com/juicebox-systems/juicebox-sdk), [Software Realm](https://github.com/juicebox-systems/juicebox-software-realm) and [HSM Realm](https://github.com/juicebox-systems/juicebox-hsm-realm). X Chat's [official help](https://help.x.com/en/using-x/about-chat) documents use of Juicebox HSM realms with hardware attempt limits. This is evidence that the *protocol family* is industry-deployed, **not** that X's HSM service is available to Mosaic.
- Software-only nodes can be hosted across independent organizations and providers, using $0 existing/free quotas if each independent party volunteers resources and maintains them. **All realms controlled by one Mosaic GitHub/cloud administrator do not create a genuinely independent trust boundary**. A hostile threshold of realms can recover PIN-testing material, and online guess budgets across different realm subsets require review. Production claims need independently administered persistent nodes, trusted upgrade/fork protocol, threat review, availability and licensing (AGPL for Go software realm).
- [Juicebox HSM Realm](https://github.com/juicebox-systems/juicebox-hsm-realm) says running its HSM design on commodity hosts is only suitable for preproduction, not equal hardware security.

**Kintsugi** ([Cambridge paper](https://www.repository.cam.ac.uk/items/ba8d3cfa-f78c-4d46-8bbe-66fc238afd18), [open-source MIT prototype](https://github.com/kewbish/kintsugi)) is a **genuine counterexample to the claim that hardware is universally mathematically necessary**. It proposes low-entropy secret recovery using threshold independently operated software nodes and may tolerate up to t honest-but-curious colluding nodes, with some nodes offline. But its prototype explicitly omits zero-knowledge proofs, ACSS degree checks, reliable broadcast, validated Byzantine agreement and persistent-bootstrap-node recovery. **Not production ready and not a complete malicious-operator/rollback solution.**

**Academic foundations**: [RFC 9807 OPAQUE](https://www.rfc-editor.org/rfc/rfc9807.html) explicitly warns that **single corrupted aPAKE servers can run offline dictionary attacks**, and points to threshold OPRFs as an alternative; [TOPPSS](https://www.research.ed.ac.uk/en/publications/toppss-cost-minimal-password-protected-secret-sharing-based-on-th/) studies threshold password-protected secret sharing. Both show **multiple genuinely independent secret-holding parties** can substitute for a specialized HSM *under explicit corruption assumptions*. This is not proof that simply putting three services under one owner's API keys creates security.

### $0 hardware already owned: TPM 2.0 caveat

The [Trusted Computing Group TPM2 architecture](https://trustedcomputinggroup.org/wp-content/uploads/TCG_TPM2_r1p59_Part1_Architecture_pub.pdf) and [Microsoft TPM fundamentals](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/tpm-fundamentals) describe hardware dictionary-attack protection, with **global** rather than per-user counters, lockout-auth reset, self-healing and other lifecycle behavior. [TCG provisioning guidance](https://medias.cdn.trustedcomputinggroup.org/production/TCG_TPM_v2_0_Provisioning_Guidance_Published_v1r1_7aa73d02ea.pdf) describes owner authorization and storage-hierarchy clearing. A spare TPM can protect a specific device-bound secret against offline copies; unlike a generic HSM vault, it is not a ready Internet-facing, multiuser, remotely attested, rollback-resistant PIN escrow. It also introduces a home-machine uptime/availability/DoS dependency. TPM presence, model, policy support, client-to-TPM session protocol and owner access in this project are unknown.

### Protected platform services and others

- [Apple iCloud Keychain escrow security](https://support.apple.com/en-ph/guide/security/sec3e341e75d/web) explicitly describes password/passcode recovery protected by HSMs and destroying escrow after ten wrong attempts. An existing platform **pays for** its own HSM fleet, so it can be *free to Mosaic users* without being an arbitrary developer-usable Mosaic PIN vault.
- [Google Password Manager passkey security](https://security.googleblog.com/2022/10/SecurityofPasskeysintheGooglePasswordManager.html) similarly protects synced credential recovery using device authentication and cloud-backed mechanisms. This is not an API exposing a custom Mosaic PIN/HSM retry counter.
- [Cloudflare Durable Objects Free](https://developers.cloudflare.com/durable-objects/platform/pricing/) can hold a normal online counter; [Cloudflare Secrets Store](https://developers.cloudflare.com/secrets-store/) can withhold secrets from normal dashboard/API reads, but a privileged project operator can still deploy code that uses them. The service has no publicly established hard irreversible per-user PIN guess limit enforced against that operator.
- [Google KMS pricing](https://cloud.google.com/kms/pricing) lists free Autokey quotas; [AWS KMS pricing](https://aws.amazon.com/kms/pricing/) lists free request quota but customer-managed key monthly charges; [AWS CloudHSM FAQ](https://aws.amazon.com/cloudhsm/faqs/) and [Azure Cloud HSM FAQ](https://learn.microsoft.com/en-us/azure/cloud-hsm/faq) explicitly say no free HSM tier. Free grant/trial/credit is not permanent no-spend.
- [Signal Secure Value Recovery open source](https://github.com/signalapp/SecureValueRecovery2), [Signal technical explanation](https://signal.org/blog/secure-value-recovery/) and the [2024 USENIX OSDI SVR3 paper](https://www.usenix.org/conference/osdi24/presentation/connell) show a deployed attested HSM/enclave answer; the research is public, **hardware is not donated as a ready free third-party service**.
- [Meta Backup Key Vault](https://engineering.fb.com/2026/05/01/security/meta-strengthening-end-to-end-encrypted-backups/) and [Messenger Labyrinth whitepaper](https://engineering.fb.com/wp-content/uploads/2026/05/Minos-Updates-2026-Encrypted-Backups-White-Paper.pdf), printed p.43, say the user PIN authenticates release from a protected vault, **not derivation of the backup encryption key**. Printed p.44 additionally documents an independent six-digit consented *device-pairing* code with three attempts (this requires another device and is not solo lost-device recovery).

### Hard edge cases any proposal must pass

1. **No offline verifier**: copy Appwrite database, Function source, full backups and available service credentials. Show why none permits unlimited PIN enumeration. Demonstrate whether an HSM/threshold secret truly remains outside the stolen set.
2. **No privileged bypass**: assume administrator can change Appwrite Function, IAM, CI, Cloudflare Worker and recovery-application code; test whether decrypt permission, code update, fake endpoints, or secret read operations bypass PIN.
3. **No retry rollback/fork**: restore old snapshots, duplicate instances, split/network-partition nodes, rotate/re-enroll credential under same identity, use alternate recovery subsets and resurrect deleted user. No new PIN attempts beyond reviewed global budget.
4. **Strong identity and frontend**: independent Appwrite fully authenticated (MFA-completed) identity matching immutable owner, replay-resistant attestation or independently operated quorum, exact approved client-to-key-holder protocol; protect against malicious same-origin JS where the threat model demands it.
5. **PIN lifecycle**: chosen PIN not printed/logged, random 256-bit content key never directly PIN-derived, cannot reset by password/email alone; true wrong attempt consumes budget, terminal lockout and emergency recovery, device loss, deletion and restoration.
6. **Cross-platform, operations, SLO**: iOS/Android/desktop browser UX, offline authorized device, existing/new user, load, free-tier rate-limit/failure behavior, multi-year uptime, backup and anti-rollback, account erasure and owner isolation, source/license/security review.
7. **Mosaic backend**: old installed PWAs must be server-fenced against legacy plaintext writes before any real-data encryption migration. Appwrite key storage and IAM do not by themselves make ordinary RxDB/task/message/photo data E2EE. User authorizes no Production changes or releases.

## Answer and recommended prioritized research path

**What is defensible today:**
- *No*, we cannot prove "no free way exists." **Oracle's Always Free HSM keys** and **Kintsugi/threshold PPSS** disprove the overbroad assertion that all useful hardware key storage and all PIN-protected protocols necessarily cost money.
- *Yes*, a genuinely no-spend design can resist **copied-database attackers** under more modest trust assumptions, likely using OCI Vault HSM or an independently hosted OPRF secret/threshold realm, if free allowance and IAM are verified and no offline PIN verifier is leaked.
- **Still not validated:** an operator-blind, highly available, freely hosted, auditable **PIN-only lost-device recovery vault** secure against a privileged Mosaic administrator controlling all participating infrastructure, mutable web JavaScript and recovery counter rollback. This is a **conditional no-go with current evidence**, not a proof of impossibility.
- **Best $0 investigation:** first audit actual OCI Free Vault quota and IAM via approved read-only connection; second, isolate the existing published **Juicebox SDK + software realm** in a synthetic offline test and model *genuine independent operators* vs a single Mosaic operator; third, analyze Kintsugi's threat assumptions and missing implementation components before considering it. Avoid building a custom PIN KDF, no paid trial, no live personal data. Keep the existing high-entropy emergency recovery-key option.
- **Decision threshold:** The owner should only be offered a "secure six-digit PIN" as a production-ready feature after a concrete service and independent threat review prove the specified attacker model. If only database-theft resistance is achievable at $0, label the reduced guarantee explicitly and seek a separate product-security decision. There is no basis for claiming all threat models are satisfied by a standard Oracle HSM key or by rate limiting in Appwrite.

**Unverified facts, not to imply as passed:** live OCI Vault usage, quotas remaining, IAM policies, existing hardware TPM, existence of dependable independent operators, production-grade Juicebox software-only deployment and associated latency/free-tier viability, actual third-party external PIN escrow API and independent security/audit coverage. No real vault service or recovery PIN was created as part of this research.

## 2026-11-18 code-level deep dive — OCI HSM versus Juicebox software realm, external review, implementation gaps

This section supplements (and where noted **corrects**) the initial candidate ranking with direct source analysis of the actual open-source server and a later X Chat publication. All links are public. No external repository tests were executed; the environment does not have network access to clone dependencies. This is **source review, not a cryptographic audit**. ### OCI Free HSM: specific capabilities that *are* and *are not* present

Official sources:
- [OCI Always Free resource allowances](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): 20 **HSM key versions across the tenancy** and 150 secrets. This does *not* include Oracle's billed virtual **private** vault product; use the regular multitenant **Virtual Vault** rather than assume a dedicated HSM partition is free.
- [Oracle key management FAQ](https://www.oracle.com/in/security/cloud-security/key-management/faq/): Vault cryptographic API calls are not per-operation billed; versions above the free HSM allowance and private vaults incur charges. The account's actual existing quotas/usage and region are not known.
- [Vault capabilities](https://www.oracle.com/security/cloud-security/key-management/): HSM master keys are nonexportable; supported remote operations include Encrypt, Decrypt, GenerateDataEncryptionKey, Sign and Verify. An encrypted **data encryption key** can be decrypted and returned to the authorized application, which may then possess that plaintext DEK. No custom multiuser PIN-verification program or immutable per-user attempt counter is exposed by the free managed key API.
- [OCI IAM Key policy reference](https://docs.oracle.com/en-us/iaas/Content/Identity/policyreference/keypolicyreference.htm): `KEY_DECRYPT` authorizes Decrypt, and `request.includePlainTextKey` controls whether plaintext generated key material is returned; `use keys` can grant decryption. Separating "ability to export the HSM master key" from "ability to invoke the HSM to decrypt a user key" is essential.

**Critical feasibility outcome:** OCI Free Vault **is not a drop-in Juicebox HSM realm**. Juicebox HSM realms run a **custom trusted recovery program**, maintaining protected PIN counters and OPRF shares. Oracle's free managed Vault API is a general-purpose cryptographic service, not a way to upload and attest a custom Juicebox realm binary. The separate [Juicebox HSM Realm](https://github.com/juicebox-systems/juicebox-hsm-realm) targets **programmable Entrust nShield HSMs** and explicitly says a commodity-host "software HSM" is for non-production tests. No direct plugin/bridge between Juicebox HSM realm and Oracle managed Virtual Vault was found, and treating an Oracle sign/decrypt API as if it were an attested stateful PIN gate would be incorrect.

The *strongest verified Oracle-only use case* is protection from copying the ordinary Appwrite database **without** obtaining the Oracle KMS key/identity. It does **not** protect against a privileged administrator who can grant themselves the app's Decrypt permission or trigger application code to perform arbitrary authorized Decrypt operations. Using a PIN check in front of the decrypt API does not solve this administration bypass or counter restoration.

**Read-only inventory blocker:** connected Mosaic Oracle tools cover host/Scratch/Production Appwrite, not an OCI tenancy Vault IAM/quota inventory. Consequently, tenant's 20-key allowance headroom, potential billable private vaults, region, current keys, audit log configuration and administrative separation are **NOT independently verified**. No OCI Vault keys or policies were created or changed.

### Juicebox software realm: actual record and state-machine inspection

Read directly from official GitHub main branch:
- [records/userRecord.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/userRecord.go) contains a CBOR-serialized `Registered` row with `OprfPrivateKey`, `UnlockKeyTag`, `EncryptionKeyScalarShare`, `EncryptedSecret`, `GuessCount`, and `Policy`. These are **software-accessible data**; they are not inside an attested HSM. One realm alone does not give the full threshold secret, but a privileged reader compromising enough software realms defeats the intended trust threshold.
- [router/router.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/router/router.go) performs PIN recovery phases explicitly:
  - `Recover1` refuses a `GuessCount >= Policy.NumGuesses` registration and transitions it to `NoGuesses`;
  - `Recover2` checks registration version, increments `GuessCount` **before** returning an OPRF response and updates the record;
  - `Recover3` compares a realm-specific `UnlockKeyTag`, transitions exhausted registrations to `NoGuesses` on failure, and **resets the counter on successful tag**.
  This is genuine online throttling, not just a UI mock. It is **not** proof of an admin-immutable counter or of a single global ten-guess limit across multiple recovery-realm combinations.
- [records/dynamoDbStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/dynamoDbStore.go) uses DynamoDB conditional version writes / compare-and-swap to avoid concurrent-lost-updates. [records/bigtableStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/bigtableStore.go) uses Bigtable conditional mutations. [records/mongoStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/mongoStore.go) uses conditional update/version. These help serialize requests but **none proves a malicious storage owner cannot restore an older snapshot**.
- [records/memoryStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/memoryStore.go) locks process memory and implements conditional writes; **restarting the process loses registrations/counters**. It is strictly a convenient local synthetic test provider. [records/recordStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/main/records/recordStore.go) exposes only `gcp`, `aws`, `mongo` and `memory` providers. There is **no native OCI/Appwrite/Cloudflare Durable Object persistent provider**; a real deployment may require paid GCP Bigtable/AWS facilities, a free MongoDB hosting allowance, or a reviewed custom adapter.
- [Official realm README](https://github.com/juicebox-systems/juicebox-software-realm) describes Go service deployment, JWT tenant signing material and dependencies on persistent provider. The server repo is **AGPL-3.0**, whereas the [client SDK](https://github.com/juicebox-systems/juicebox-sdk) is **MIT** with Rust, JavaScript, Android and Swift bindings. Network-served modifications raise AGPL compliance obligations; obtain ordinary legal review when modifying or distributing.

**Practical consequence:** We can **evaluate Juicebox locally for $0** (using synthetic data and in-memory instances), but that does **not** verify free, independently administered, persisted, secure, highly available production recovery. Every authentication/recovery token must be bound to the immutable correct Appwrite owner after completed MFA; server-issued realm JWTs must not be a way to re-register other users or reset their recovery credentials.

### Multiple realms do not automatically mean one global attempt counter

The [Juicebox 2025 protocol paper](https://eprint.iacr.org/2025/348.pdf) describes a per-realm allowed/attempted guess count, counter reset after proof of the correct PIN, thresholds greater than one, and trusted nonvolatile HSM hardware for preventing rollback.

Cryptographer [Matthew Green's June 2025 analysis](https://blog.cryptographyengineering.com/2025/06/) identifies:
1. **Subset amplification:** If a recovery can use different subsets of realms, the same nominal 10-per-realm count can allow **more than ten aggregate guesses** unless counts/participation are coordinated.
2. **Honest-user reset:** A genuine correct PIN use resets a realm's counter, which can permit an adversary to distribute guessing between authentic recoveries (normal industry tradeoff; detect anomalous attempts).
3. **Realm ID/tag confusion threat:** His post discusses a hypothetical malicious fake realm using the same identity as a real one to obtain a PIN-derived reset tag. He and the protocol designer said practical checks may prevent this; it is **not an independently demonstrated exploit**, but it reinforces strict pinned endpoint/key/realm identity and source review.

**Illustrative bound, NOT a measured Juicebox test:** For N=3 realms, threshold T=2, each realm allowing 10 unsuccessful attempts, an adversary able to choose distinct realm pairs may distribute 5 attempts to each pair (AB, AC, BC) for **15 total attempts** while each realm sees only 10, assuming no coordination/counter resets. With T=3 of 3, all participating realms see every attempt (at the cost of zero tolerated realm outages). Real Juicebox recovery/version/OPRF rules require independent evaluation; this arithmetic demonstrates why "10 per realm" is not automatically "10 per user globally". If the product requirement is an exact global bound, independently coordinated rollback-resistant counters or stricter quorum/availability tradeoffs are required.

**Threshold trust requirement:** The protocol's [software-realm README](https://github.com/juicebox-systems/juicebox-software-realm) itself recommends realm providers maintained by **different authorities**. Three VMs in three accounts whose ultimate credentials and deployment keys are controlled by Mosaic's same administrator **do not** satisfy a noncolluding-party assumption. For truly independent free operators, obtain independently controlled principals, guaranteed persistence/online availability and explicit policies for shutdown and key rotation. A quorum service can still be denied by an uncooperative party; without emergency recovery a PIN-only user may lose the ability to access encrypted data.

### X Chat production precedent — chronology correction and limits

**Important correction to earlier simplified checkpoint:** Matthew Green's **June 2025** report questioned whether X had genuine HSM realms and noted the original Juicebox project reportedly shut down. That report **preceded** X's subsequently published HSM ceremony, documentation and external audit:
- [X Chat official documentation](https://help.x.com/en/using-x/about-chat) now describes **3 realms, 2 HSM-backed, 2-of-3 recovery** and **20 attempts**, with all recovery paths including at least one HSM realm.
- [X Chat cryptography primer](https://github.com/xdevplatform/docs/blob/main/xchat/cryptography-primer.mdx) explicitly says all three realms are X-operated but two HSMs prevent ordinary X administrator access under the hardware's trust assumptions.
- [X's HSM realm key ceremony description](https://x.com/Engineering/article/1971739456857145574) was published after the 2025 criticism. It describes programming-card destruction and hardware setup procedures; **independent reproduction and continuously running hardware measurements still need verification**.
- [Trail of Bits official publications index](https://github.com/trailofbits/publications/blob/master/README.md) includes an October 2025 X Chat review published December 2025, which X links in its documentation. The audit PDF's exact findings were **not independently read in this research environment**, so its existence does not certify every PIN-vault attack was addressed.

**Conclusion:** X's public claims and published materials make HSM-backed Juicebox a meaningful deployed *reference*, but **do not** show that deploying the Go software realms alone under a single Mosaic owner reproduces those hardware guarantees. Current source activity is mixed: public GitHub indexed an SDK update in August 2026; an independent 2025 analysis described the original organization as shut down. Treat long-term OSS support and security patch ownership as **unverified**, not automatically supported or abandoned.

### Kintsugi closer reading

The [Cambridge-hosted paper](https://www.repository.cam.ac.uk/items/ba8d3cfa-f78c-4d46-8bbe-66fc238afd18) states recovery nodes may be independent organizations or end-user devices, and the protocol seeks resistance to offline password guessing without a secure hardware requirement when sufficient parties remain honest. The [MIT research code](https://github.com/kewbish/kintsugi) is a Rust/Tauri/libp2p **desktop demonstration**, not a ready multitenant browser/production vault.

Prototype limitations enumerated by its author: missing zero-knowledge checks, ACSS polynomial degree checking, reliable broadcast, multi-valued validated Byzantine agreement, and persistent bootstrap-node recovery. These are material if Mosaic's threat model includes actively malicious nodes and persistent recovery across crashes. **Do not reuse the demo's assurances as production guarantees**, even if its underlying cryptographic research is credible.

### Revised prioritization

**1. Most immediately useful:** Verify real OCI Always Free Vault quota/IAM through a read-only Oracle tenancy surface. Treat this as **database theft resistance**, not operator-blind E2EE. Determine whether key grants remain entirely under Mosaic administrator control (likely, but actual IAM unverified).

**2. Most useful reusable protocol research:** Evaluate Juicebox's MIT SDK and AGPL Go software realm in fully synthetic local tests. Validate counter behavior/rollback and credential isolation; explicitly account for missing OCI provider and independently administered persistent realm hosts. Source was inspected; tests and deployment were not performed.

**3. Strongest potential true no-HSM operator resistance:** Threshold independent software guardians using reviewed Juicebox/Kintsugi-like approaches. This is conditional on genuinely separate trusted operators and assured availability, not simply free cloud VM counts. Current Kintsugi prototype is insufficient for production.

**4. If no independent hardware/guardians are available:** Stop short of PIN-only lost-device recovery and keep independently generated high-entropy recovery keys / authorized-device pairing. No software trick can make an offline-copyable, PIN-only ciphertext enforce an irrevocable retry limit. Avoid app operator claiming Signal/Meta-equivalent protections.

**Updated verdict:** **hardware is not universally mathematically mandatory, and some hardware cryptographic key storage is free**. But OCI Free HSM + self-operated online counter is **not** a secure six-digit PIN-only operator-blind recovery vault; and Juicebox's source code alone does not supply a free, independent, reliable operator quorum. A secure $0 implementation remains an **unvalidated engineering possibility conditional on external trust and operational availability**, not a ready service or proof of infeasibility.
