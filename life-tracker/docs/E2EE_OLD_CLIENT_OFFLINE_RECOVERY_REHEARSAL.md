## Verified source-level behavior and unresolved risk

- Current `src/db/ownerWriteCas.ts` only falls back to direct `updateRow` for explicit HTTP 400 / `Unknown action`. An authenticated M2 HTTP 409 is thrown. Owner create action also propagates 409; it does not reach `createRow` fallback. This is not yet proof of physical older installed-client behavior.
- Task/category/Diary RxDB replication push handlers must propagate cutover failures rather than returning a successful conflict or performing a direct plaintext fallback. Unit tests in the current task assert the relevant **handler** contracts for create/update. RxDB's durable actual pending checkpoint and local IndexedDB survivability still require separate integration/device proof.
- Generic `src/lib/outbox.ts` **drops** entries on permanent HTTP 4xx, including HTTP 409; its current primary consumer is `src/lib/socialOutbox.ts` (friendship/social actions, separately scoped M3). This is an observed data-loss *risk* on a historical queued action, not proof that an old installed PWA has such an entry. Do not interpret generic outbox behavior as the task/Diary RxDB queue implementation.
- Table-level `$permissions=[]` with rowSecurity does **not** prove previously created rows with individual update/delete grants are immutable. The signed M2 Scratch floor currently requires all six legacy tables and old image bucket to be empty. **Do not provision a historically granted test row in this shared Scratch project**, which would violate the release invariant. Test row-level old permission closure only in a separate, explicitly provisioned disposable/reversible environment with an exact reviewed cleanup and root-source gate.

## Local Chromium encrypted-outbox persistence rehearsal (new client only)

The source-only task adds `tests/e2e/e2ee-owner-outbox-offline.spec.mjs`, run against a local Vite host with **real browser IndexedDB + WebCrypto** and blocked outbound Appwrite requests. It stages one disposable owner-private ciphertext task, reloads the document, verifies exact op ID/nonce/ciphertext persistence, confirms separate owner/project isolation, propagates an injected HTTP 409 without deleting the intent, preserves it after a lost authenticated readback, and removes it only after a simulated duplicate acknowledgement plus successful local AEAD-verified readback. No Appwrite credentials, Function executions or stored server records are used.

Passing this browser contract advances **new encrypted-outbox local durability**, not actual historical installed-PWA RxDB/offline recovery, nor old row-level permission closure. Those still require the independent manual/device and disposable-backend acceptance below.

## Safe exact-source rehearsal sequence — requires separate live owner/device evidence

1. Identify a real **previously installed** PWA binary/controller and immutable version SHA that historically writes the six owner-private domains. Verify its configured project/origin, origin registration, service worker active+waiting status, and data-store namespace. A new preview compiled from old source is not automatically a substitute for an installed old controller.
2. Use disposable accounts only, separate browser profiles and a **separate disposable backend partition** with reviewed direct-write permissions/row canaries and rollback. Never use normal Preview, dev, main, Production, or the live Scratch synthetic-owner root/data to manufacture old row-permission states.
3. While the old PWA is offline and before its network is restored, queue a task create, private Diary edit, and task tombstone in its real local store. Record local IDs, revisions and a synthetic-only local receipt without exposing plaintext in logs or operator telemetry. Preserve local storage; do **not** clear site data, uninstall the PWA, or force service-worker activation.
4. Capture a **local recovery snapshot/export** of every unsent revision before reconnecting an old client to a sealed backend. Any recovery format must be client-side encrypted/authenticated using the current owner's root or held entirely offline until an equivalent reviewed encrypted transfer exists. Do not upload plaintext snapshots to Appwrite, GitHub or CI logs.
5. Reconnect old PWA under controlled network interception to the cutover backend only after the recovery snapshot is verified. The old action must fail with exactly the expected cutover reason; any direct row update/delete or image upload must be rejected. Verify on-server zero plaintext canaries, zero new old Storage files, and unchanged encrypted content.
6. Reopen old local store: queued edits, tombstones and pending images must still be recoverable without destructive service-worker cleanup. If any are missing, **STOP** and preserve the frozen client/device backup; do not force another retry or change shared server ACLs to allow plaintext.
7. Upgrade through normal signed PWA flow only after a verified local recovery/import path exists. Verify the exact new controller, restoration into encrypted owner intents, readback and AEAD decryption, idempotent retries, account isolation, and no duplicate or lost edits. Confirm revoked/stranger data is denied and no private data reaches logs/push/DR/plaintext.
8. Only after a separate row-ACL negative test with a synthetic historic pre-created row is independently read back should old-row update/delete be marked PASSED. Return that isolated environment to an independently verified empty state before any release gate.

## No-go criteria

Missing old controller SHA, absent locally verified backup, any ambiguous HTTP status, any successfully persisted legacy plaintext, incomplete row ACL cleanup, missing old queue after denial, cross-owner access, or rollback that reopens plaintext writes. Keep the existing 7/7 and 3/3 results as **separate accepted narrow gates**. Normal E2EE sync/cutover, Production, DR and erasure remain blocked until their own acceptance.
