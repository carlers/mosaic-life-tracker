# #2084 read-only legacy queue snapshot collector — 2026-11-26

Source-only adapter \`src/lib/e2ee/localPendingQueueSnapshot.ts\` reads the **three currently known** localStorage pending-queue formats: per-entry and legacy array forms of \`mosaic_social_outbox\` and \`mosaic_message_action_queue\`, plus \`mosaic_friendship_commands_v1\`. Exact owner-bound entries are collected into the already staged WebCrypto root-encrypted local pending capsule without any deletion, migration, replay, remote calls, IndexedDB mutation, or UI. Unrelated accounts are excluded. Unknown/malformed owner entries, mismatched IDs, conflicting legacy/new values, missing storage keys and observed concurrent changes fail closed. A second raw read after asynchronous encryption checks whether visible queue bytes remained stable.

**Severe remaining limits:** This only recognizes currently documented localStorage queue formats. It does **not** capture pending RxDB/IndexedDB task/diary changes, pending photos, stale service-worker controllers, other historic namespaces, all origin/profile storage, or post-return cross-tab races. A source-only collector cannot fix historical installed clients, furnish a verified human-downloadable offline file, authenticate exact Appwrite account state or establish a lossless encrypted restore. Historical PWA reconnection stays BLOCKED until independent complete recovery and rollback tests. No Production or normal Preview backend changes. Track #1662/#2084.

## 2026-11-26 — pending queue durability follow-up

The previous shared outbox evicted the oldest pending action when a user exceeded 100 entries, returned successfully when localStorage refused a new write, and deleted the raw legacy array even when some entries were malformed or could not be written. The isolated E2EE task branch `chatgpt/2084-lossless-outbox-cap-storage-20261126` changes this to explicit **fail-closed queue-full/storage/recovery errors** without deleting existing pending intents. It permits replacement of a recognized same-key item at capacity; refuses overwrite of malformed same-key payloads; verifies storage readback before declaring an enqueue accepted; requires every legacy array item be parsed and persisted before removing the old array; and blocks further enqueue if the old array cannot yet migrate. Focused tests cover these cases and consumer caps. This is **not** proof that every historical installed PWA or all RxDB/image writes are recoverable, and it does not change the actual signed E2EE Scratch old-writer fence.

The general outbox's existing five-transient-failure drop/revert policy is **still a separate loss-risk audit item** for complete lossless recovery; this batch does not change its retry semantics. Explicit account-erasure cleanup of unreadable legacy entries also needs a separate data-isolation review. Do not cut over an account or claim complete encrypted recovery on these source-only changes.

## 2026-11-26 — transient delivery exhaust safety

A further isolated E2EE source-only patch changes the opted-in social/message outboxes to **hold** original pending intents after five transient server/network failures instead of dropping/reverting them. The hold is persisted with the original payload and attempt count, blocks same-owner enqueue/replay after reload, and does not affect unrelated owners. A volatile in-memory latch also blocks same-session replay if persisting a hold fails, although unavailable browser storage cannot guarantee persistence across a full restart. Permanent non-cutover 4xx behavior and default generic-outbox retry semantics remain unchanged. This is a conservative halt requiring a future reviewed recovery UX, not an automatic retry or evidence of finished encrypted messaging.

The recovery-preserving outbox also stops dispatch of later same-owner queued actions on each transient failure, maintaining FIFO order rather than allowing dependent actions to overtake an unacknowledged earlier action. The existing tests exercise two queued intents and require only the first to be retried before the persistent hold.

## Retry-hold storage compatibility (2026-11-26)

Opted-in encrypted-cutover-sensitive queues treat the persisted fifth failed attempt as a durable recovery hold. No additional `deliveryHold` JSON flag is necessary. Existing `encryptionCutoverHold` remains the distinct signed HTTP 409 state. This reduces Home bundle code while retaining no-replay after reload and owner-scoped FIFO tests. Generic non-E2EE retry/drop behavior is unchanged. A failed persistence attempt cannot guarantee a hold across a browser restart; recovery must still fail closed.
