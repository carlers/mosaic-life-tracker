# Oracle-first Mosaic release — minimum verified migration path (#975)

Decision: **prepare self-hosted Oracle Appwrite as the next primary backend**; preserve the existing Supabase recovery implementation as a non-live contingency. This document neither approves Production changes nor asserts that users have migrated. Only directly blocking security and data-preservation gates stay on the fast launch path; do not repeat broad DR-volume inventories.

## Current verified facts (2026-10-30)

- Appwrite Cloud project `6a9703c50016b37110ff` reports `paused` through the connected Appwrite Console. No live Cloud export is verified. Native migration requires the Cloud source to be available and the destination self-hosted instance publicly reachable; it resets `$createdAt` and `$updatedAt` (see official Cloud migration docs).
- Oracle ARM64 VM runs Appwrite 2.6.2 with PostgreSQL, Redis and ClickHouse. Disposable Oracle project `6ae1bf2e00034572451b` has **already been provisioned with 14 tables, a storage bucket, and a Function**; it is not an empty DR restore destination. Existing `scripts/dr-restore.mjs` correctly refuses a populated destination, so do **not** force it into this project or clear existing resources.
- Historical original Appwrite DR `mosaic-dr/v1` encrypted R2 generations with authenticated privacy-deletion markers exist per prior independently verified snapshots. The latest backup may *not* include phone edits made during the Appwrite outage, and restored Auth users may be a strict subset because deleted-account markers take precedence.
- The owner's **installed phone PWA has unique offline changes**. Original PWA's endpoint and project ID were compiled for Appwrite Cloud; simply tapping Sync cannot point old JavaScript to Oracle. A new Oracle-built PWA may use a different local database/session context. Do not uninstall, logout, replace, clear old PWA storage or overwrite its offline records. Export two separate protected ZIP copies with locally available photos first. Validate the actual exported ZIP version and missing photos. Keep the phone's original installation until owner-data parity is confirmed.
- Mosaic personal ZIP **Replace** intentionally tombstones destination-only personal records, even with a safety snapshot. Use signed-in owner-verified **Merge** as the default after archived/migrated server data are present. Existing friendship/grant/message state is not in a personal ZIP and must come from proper backend restore or be explicitly deferred. Preserve row owner IDs and tombstones. Never use a ZIP's self-declared user ID as independent ownership proof.
- Oracle-only preliminary R2 snapshot was independently byte-read-back for four age ciphertexts but is not a coordinated current-state full Appwrite DR image. A basic current restorable backend/data checkpoint is still required before public users; full all-service cold snapshot/watchdog engineering can be deferred from the MVP.

## One owner command for source readiness (not migration)

On a clean exact-SHA project checkout with Node/npm dependencies installed, run `bash scripts/oracle-source-preflight-fedora.sh`. It uses interactive hidden prompts for the **original Appwrite Cloud DR** R2 reader and DR AES-256 key, not Oracle's newer `age` encryption identity or Oracle-only R2 bucket. If original R2 environment is already set privately, it can use it without re-prompting. Never paste secrets into chat, GitHub, shell commands or logs.

This wrapper invokes `node scripts/dr-restore.mjs --preflight-only --latest`. The mode discovers the most recent timestamped `COMPLETED` generation, verifies signed encrypted manifest and all referenced encrypted object/file bytes, authenticates the separate permanent-erasure markers, counts only eligible user/DB/table/bucket objects and checks whether surviving account password hashes use the currently implemented Argon2 restore path. It outputs **only sanitized aggregate counts and fixed statuses**. Invalid latest generations fail closed; it never falls back silently to an older snapshot. It does **not** create/modify an Appwrite project, connect to Oracle, restore any data, recover phone-only edits, prove owner login or change endpoints. It is not proof that public migration is ready.

## Shortest safe next steps after source preflight

1. **Select one verified source.** If Appwrite Cloud becomes readable, prefer official Cloud-to-self-hosted migration only into a deliberately reviewed fresh target. Before using it, record its timestamp-reset behavior and verify source/target IDs, grants, Auth and file counts. If Cloud is still paused, use the original encrypted DR source only if the source-only preflight passes and its eligible accounts/data are confirmed to cover the intended owner(s). Avoid reimporting erased accounts. If coverage is incomplete, offer new consented accounts as a **separate**, explicitly limited beta; do not call it migrated user history.
2. **Recover into a fresh isolated Appwrite target** and validate Auth and owner-only data with the existing `dr-restore.mjs` **exact source project, project ID confirmation, private read-only R2 credentials, and fresh target-scoped API key**. Never run the DR restore against the already-populated Oracle disposable test project, the original source project or Production. The native Appwrite migration from Cloud is a separate mode and is not yet executable against the paused source. Function/SMTP/platform endpoints require separate validated provisioning after DR data restore.
3. **Preserve phone changes.** Require two untouched private ZIP exports. Reauthenticate the original migrated owner on the Oracle-connected app; ensure owner ID match or independently approved binding. Merge only, with connected-target fresh sync before writing; verify categories/tasks/tombstones/photos and compare per-owner record counts across phone and server. Do not enable two backend writers or assume an old offline PWA was redirected to Oracle automatically.
4. **Basic go-live security, not exhaustive hardening.** Stable HTTPS with trusted certificates, correct Web platform origins/CORS, no public database port, rollback-reviewed rotation of the known upstream-default PostgreSQL role password, functional reset/confirmation SMTP, approved message-action active deployment, private file access, explicit two-owner denied cross-account access, offline→online sync and functioning real mobile PWA. Capture a **current** independently recoverable encrypted Auth/DB/media/config checkpoint before public user cutover. Do not weaken source and release gates, disclose secrets, or expose a privileged SSH/Docker control path.
5. **Owner approvals, then release.** Approve actual Oracle credential/HTTPS/backend writes and any real-user import separately; verify canonical CI, disposable browser/device acceptance, target-specific data recovery, rollback/old-client fencing and then obtain explicit approval to promote `dev` to `main` and alter Production. No release 1.0 without separate approval.

## Deferred, not discarded

Full 19-container stop-order/Redis/ClickHouse cold snapshot watchdog, advanced observability and capacity tuning, Supabase promotion and automatic cross-provider failover, new social feature work and routine Appwrite Cloud reactivation may follow the core release. A historical paused Cloud project and a separate Supabase project are **not automatic failover or offsite backups** without proven ongoing state transfer and recovery. R2 remains the offsite ciphertext storage.
