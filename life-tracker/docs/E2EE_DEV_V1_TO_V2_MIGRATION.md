# Owner-v1 to owner-v2 local synthetic migration proof

Issue #2084, staged only under current-dev E2EE security draft. No network calls, Appwrite client, background sync, account mutation, restore or automatic reconnect.

`prepareScratchOwnerV1ToV2` first AEAD-decrypts the exact six-domain isolated Scratch v1 ciphertext with the historical routing AAD, derives a deterministic new root/HMAC-bound opaque ID from its original local ID (not from the public v1 row ID), seals all current-v2 private fields under the v2 policy AAD, and verifies local decryption returns the *complete original document*. Unclassified legacy fields **fail closed** rather than being dropped. It generates fresh v2 revision and operation ID and produces an immutable proposed ciphertext intent. The entire intent must be **durably stored before an eventual remote PUT**: repeated fresh preparation derives the same destination ID but different nonce/revision/op ID, so calling it twice is NOT idempotent without the durable outbox. `verifyScratchOwnerV1ToV2` independently authenticates both historical v1 and future candidate v2 readback against that persisted plan and the same semantic source record.

This is **not** a cross-device migration, transaction, signed server receipt, actual remote readback, complete older installed PWA offline state, secure social protocol or v1→v2 production cutover. A future migration orchestrator must persist an exact owner-scoped ciphertext intent and operation ID, obtain a real v2 Function CAS response and independent remote GET, verify server-only owner ACL and old-v1/future plaintext-writer fence, ensure all records including media and deleted/queued state migrated, then move per-account sealed floor only after a separate all-device acceptance. No v1 deletion, v2 table installation or Function activation is authorized by this source library.
