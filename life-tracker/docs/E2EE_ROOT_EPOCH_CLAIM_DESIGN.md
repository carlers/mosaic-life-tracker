# Isolated E2EE owner-root epoch unique-claim candidate — NOT installed

Tracking [#2083](https://github.com/carlers/mosaic-life-tracker/issues/2083) and [#2087](https://github.com/carlers/mosaic-life-tracker/issues/2087).

**Status on 2026-11-27:** source-only, disabled, unregistered and NOT imported by an active Function. No Appwrite mutation. There is no installed atomic root-generation CAS, secure device approval, E2EE user launch or old-client plaintext writer floor.

## Why it exists

[Appwrite issue #14489](https://github.com/appwrite/appwrite/issues/14489) reports that Appwrite 2.5.0/PostgreSQL with multiple API nodes can let competing staged read/update claim transactions both report commit success due to time-based conflict checks missing concurrent changes before visibility. The reporter observed **zero two-winner cases in 180 rounds** when a unique deterministic-ID claim row was created *in the same transaction* as the competing update. This is an upstream-reporter experiment, not proof about the installed Mosaic backend. [Appwrite TablesDB transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions) document staging a row CREATE with transactionId; generic documentation does not prove installed transaction isolation.

## Unwired source artifacts

- The server-side pure planner in appwrite-functions/message-action/e2ee-root-epoch-claim-candidate.js computes an Appwrite-safe 35-character claim ID from a SHA-256 hash over a domain-separated canonical tuple: exact Scratch project ID 6b00671500279e901846, owner ID and **expected previous generation**. The unique ID must not depend on the request operation ID, new key ID, nonce, wall clock or encrypted root envelope, so competing proposed changes for the same epoch cannot choose disjoint claims. This helper performs no writes, network calls or authorization.
- e2ee-root-epoch-claim-schema.js describes an **unregistered and disabled** table owner_root_epoch_claims_v2 with empty table permissions, row security, owner/previous generation index and server-computed SHA-256 hashes of the wrapped envelope before/after. No migrator or active Function imports it. The row IDs and metadata are not signing keys, relay approvals or proof of encryption.
- The handler unit suite tests deterministic same-owner/epoch claim collision despite different proposal key IDs/op IDs, different owner and epoch separation, exact Scratch project refusal of Preview/Production, malformed request rejection, key-length bound and disabled schema.

## 2026-11-28 additional dormant security gate — independent root possession

The prospective transaction candidate now **fails closed** unless the trusted backend integration provides both an opaque canonical authorization proof and an independent trusted server-side proof verifier. Neither can be inferred from a successful Appwrite login, MFA session or the client-supplied key ID. The verifier receives a frozen server-computed root-change transcript (exact Scratch project and owner, deterministic claim ID, old/new epochs and key IDs, operation ID, and SHA-256 of both wrapped-root envelopes) plus only the untrusted opaque proof, not the decrypted root. It is consulted before transaction staging and again immediately before commit; revocation during staging must roll back both operations. It never writes the proof to a claim row.

**This gate is deliberately still unusable in the live Function.** Neither a registered trusted-device signing-key directory, independently reviewed signature algorithm, attested root-possession challenge, nor atomic one-use proof journal exists. Unit tests inject an explicitly synthetic always-true verifier and separately exercise absent, invalid, denied and midflight-revoked authorization. These tests prove only failure and transcript wiring, **not** real possession, one-time replay safety, secure approval or installed backend isolation. The final protocol must be security-reviewed before connecting this API; do not silently substitute an MFA check for the missing verifier.

## 2026-11-28 bounded adversarial contention contract (not executed on Appwrite)

The source-only scripts/e2ee-root-epoch-race-contract.mjs exports checkScratchRootEpochRaceModel with an injected test adapter, **no credentials, server URLs or built-in network/write capability**. It limits tests to the exact isolated Scratch project and between 20 and 90 simultaneous contenders for the *same deterministic owner+old-generation claim*. It requires one recorded committed result, all other contenders to return an explicit 409 conflict, exactly one matching durable claim and next root generation on readback, and a confirmed fixture cleanup after a **positively attested disposable setup**, including when an attempt fails. If initial fixture attestation fails, the adapter does not delete an owner by ID; a trusted operator must reconcile the unknown setup state without assuming it is disposable. Uncertain receipts, duplicate winners, unexpected owner/root/key/digest, wrong project, missing prior-root setup or failed cleanup are hard failures. The counterpart unit suite uses synthetic in-memory fake adapters, including deliberately corrupt receipts and forged winner counts.

Passing fake-port tests is **not** proof of the installed backend's transaction serializability. A separately reviewed Oracle host adapter must attest the actual Appwrite image/version, Docker API-node topology, TableDB and Postgres version, exact Git source, root-only project authorization, verified disposable MFA test account, genuine device-held proof, original ciphertext semantics, and its own cleanup before and after *real* concurrent test operations. It must not touch the existing signed v1 single-synthetic root/data, widen ALLOWLISTs, run on Preview/Production, or bypass private CI. The synthetic probe's invented envelope SHA256 values are not actual ciphertext and must be replaced by independently verified genuine encrypted fixtures in any real test adapter. Multiple layers of independent backend evidence remain required before source/Function activation.

## 2026-11-28 server-only claim ACL and unexpected-field readback check (UNWIRED)

The dormant root-generation transaction candidate now refuses a postcommit claim unless the persisted claim row retains an **empty per-row permissions array** and exclusively the eight reviewed owner/generation/key/operation/ciphertext-digest columns plus known Appwrite system metadata.
