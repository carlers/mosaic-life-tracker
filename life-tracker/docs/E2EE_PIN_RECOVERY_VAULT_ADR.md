## 2026-11-17 product clarification — prioritize E2EE + separate six-digit unlock PIN, defer passkey/biometric UX

**Current controlling owner intent:** First implement a genuinely encrypted-data **unlock gate** after normal Mosaic authentication, with a user-chosen six-digit **Mosaic** PIN and **$0 added spend**. Fingerprint, Face ID, hardware-passkey login and synced WebAuthn PRF integration are **deferred**; earlier candidate sections below are only research, not the currently approved UX direction. No paid enclave/vault, PRF integration, full-app migration or backend mutations were authorized by this assessment request.

### Architecture: authenticated does NOT imply decrypted

Separate the following states: (A) signed out: no account API access, no decrypted user content; (B) **signed in but encrypted content LOCKED**: Appwrite session valid for non-sensitive account identity/security operations; client account root/record keys unavailable to the application; decrypted RxDB/IndexedDB caches, search indexes, UI previews and offline drafts **must not expose content**; (C) **signed in and UNLOCKED**: after a verified local cryptographic unlock, client holds the random account root for authorized data access; (D) locked again on logout, switch account or defined inactivity/background timeout, with in-memory key invalidation and plaintext cache protections. Offline unlock on an already enrolled device is desirable; no need to round-trip to the provider to verify a local PIN when the actual key secret can remain protected.

Only non-sensitive settings, sign-out, account recovery and related operations should remain usable while encryption is locked. Password changes, visibility/share changes, device addition and encryption/PIN reset are **sensitive operations** requiring separate confirmation/reverification and where applicable the unlocked account key. Locked state must block mutation pathways that could emit plaintext via old sync or notifications.

**This is a valid product security UX, not a mandatory property of E2EE.** Modern apps often retain a protected device key and decrypt automatically after normal device/session unlock; Signal's PIN protects recovery of profile/contacts/settings but **not chat-history recovery** and is not required to view each chat after every app sign-in ([Signal PIN FAQ](https://support.signal.org/hc/en-us/articles/360007059792-Signal-PIN)); its Screen Lock is another control ([Screen Lock](https://support.signal.org/hc/en-us/articles/360007059572-Screen-Lock)). Messenger's six-digit PIN is principally a method to restore encrypted chat *backup* on additional/lost devices ([Meta product explanation](https://about.fb.com/news/2024/03/end-to-end-encryption-on-messenger-explained/)); existing-device sessions need not require re-entering it every time. Mosaic may intentionally require an explicit unlock step after every fresh account login without representing that requirement as necessary to achieve E2EE.

### Risk-aware $0 key separation

- **Actual encryption:** generate a high-entropy random 256-bit account root on the authorized client. Use versioned, authenticated encryption with fresh randomness, per-record context/owner binding and separate child/record keys. Never derive protected content encryption keys directly from a six-digit PIN or the ordinary login password. Provider storage and Function APIs receive only ciphertext and permitted metadata.
- **Existing enrolled device:** keep a separate high-entropy device-bound secret (preferably genuinely hardware-protected when supported by audited platform APIs), and use a reviewed scheme combining that secret with the *independent six-digit Mosaic PIN* to authorize unwrapping the random account root. A database-only attacker without device secret cannot brute-force the six-digit PIN against a provider-stored envelope. Use independent failure throttling, cross-tab locking and no PIN/secret logging. A UI-only PIN modal with a root already decrypted behind it **does not enforce the requested protection**.
- **PWA-specific limit:** Browser IndexedDB and a Web Crypto "nonextractable" key are not automatically Secure Enclave/Android StrongBox, nor do they prove device-specific anti-extraction or hardware-enforced retry limits. Same-origin malicious JavaScript can still invoke cryptographic operations; full local profile theft and browser compromise are harder threats than stolen cloud ciphertext. Therefore on the current React/Vite PWA, a PIN+browser-kept secret can be tested as a **qualified privacy unlock** against passive server-data compromise, but cannot be advertised as universally tamper-resistant offline PIN security. Achieving equivalent native-device assurance later may require reviewed platform keystore integrations. [OWASP low-entropy-key guidance](https://mas.owasp.org/MASWE/MASVS-CRYPTO/MASWE-0014/), [Android Keystore](https://source.android.com/docs/security/features/keystore), [Apple Keychain](https://support.apple.com/en-mt/guide/security/secb0694df1a/web).
- **New device or lost all devices:** the same six-digit PIN alone **cannot safely recover the account root from Appwrite-stored ciphertext** within the original operator-resistant threat model at $0. Require a separately backed-up high-entropy recovery key, or consented key transfer from an existing unlocked device. A standalone PIN-only recovery experience requires a protected, nonrollbackable, rate-limited vault or an independently verified equivalent; no genuinely $0 suitable service has been validated. No silent key resets, plaintext downgrade or pretending that a login password reconstructs E2EE keys.
- **Emergency key design:** treat high-entropy recovery as the cryptographic fallback, used when previously enrolled device or local storage disappears. If forgotten and no trusted device remains, protected data can become irrecoverable even though account login succeeds. Encryption key availability and account recovery are separate.
- **Adversary limits:** ordinary account authentication never reveals the root to Appwrite. Malicious client code served by the app operator remains an unsolved concern for a browser-based E2EE threat model: the provider can potentially replace JavaScript to capture the PIN/root once the user unlocks. This limitation must be explicitly described before claims of operator-proof E2EE.

### Staged acceptance for proposed UX (no authorization to skip any)

1. **Document root and threat model against current live dev.** Catalogue all client-side plaintext caches, ordinary Diary/task/category/message/bucket/settings/photo storage and server-side consumers. Decide which *metadata* may remain exposed and what settings remain usable during locked state.
2. **Synthetic isolated 6-digit local PIN proof:** build/test an actual client-root lock/unlock gate on an enrolled disposable Scratch account, using a device-held random secret + user PIN and independent high-entropy recovery key; verify account password alone cannot access decrypted content. Verify wrong PIN, brute throttling limitations, zeroization, reload/refresh, logout, multi-tab, offline and clearing browser storage. No PIN-only recovery via cloud. A server or script bypass must be treated as failure, not hidden by a PIN dialog.
3. **Real PWA security review:** prove what browser-side key storage does and does NOT resist. If device-held secret cannot be protected to the agreed attacker model, stop rather than falsely marketing the design. Do not claim Web Crypto nonextractability is hardware-backed. Include injected-script/cross-origin/key-exfiltration cases in written risk acceptance.
4. **Existing/new-account onboarding:** new users set and confirm their independent PIN as part of **encryption** setup; existing users get resumable opt-in and transparent progress; unlocked device stays usable while active, logout/defined timeout locks; brief optional periodic recall reminders only if they do not create an offline-verifiable PIN record. Account sign-in remains unchanged; biometric/passkey integration **deferred**.
5. **Full application rollout:** server-enforced block of legacy plaintext writes, encrypted domain-by-domain contract and migrations, sharing recipients' key distribution, offline changes, historical PWAs, notifications/search, account erasure and DR. Do not keep legacy RxDB plaintext while saying that a PIN secures local user data.
6. **Exact SHA, Scratch, CI + user/device acceptance:** no final Preview claim until actual source, migration, trusted server enforcement, key isolation, browser tests and provider trust assumptions pass. Separate Preview→dev→main owner approvals remain mandatory.

**Current decision:** The requested authenticated-but-locked **UX is sound** and can be prototyped with $0 added infrastructure on disposable Scratch data. **The safety of cryptographically binding a six-digit PIN on all supported PWA devices is unproven**, and a six-digit PIN **alone** as a universal cross-device recovery secret is **not safe** with an ordinary Appwrite envelope. Pursue the distinct PIN as an *enrolled-device unlock gate*, keep high-entropy fallback recovery, defer biometric/passkey work, do not confuse PIN prompting with automatic E2EE security.

## 2026-11-17 owner clarification: a **distinct Mosaic six-digit PIN** is required (current preferred $0 research direction)

**This section supersedes the previous $0 addendum's recommendation to replace the Mosaic PIN with the phone/provider PIN.** The owner is correct that Signal separates its app PIN from screen lock and that Messenger allows a separate six-digit recovery PIN. Primary sources: [Signal PIN help](https://support.signal.org/hc/en-us/articles/360007059792-Signal-PIN), [Messenger encrypted recovery](https://about.fb.com/news/2024/03/end-to-end-encryption-on-messenger-explained/). Distinctions matter: Signal's PIN recovers contacts/profile/settings, **not historical message contents**; Messenger's PIN unlocks backed-up message history via a [dedicated hardware-protected Backup Key Vault](https://engineering.fb.com/2026/05/01/security/meta-strengthening-end-to-end-encrypted-backups/) with an anti-guessing mechanism. Neither merely hashes a six-digit PIN and stores a recovery envelope.

**New design candidate:** A separate six-digit **Mosaic recovery PIN** plus a **synced WebAuthn-PRF passkey secret** as an additional, independent high-entropy recovery prerequisite. User experience:
1. **Account authentication** remains independent: password + optional MFA today, or later native passkey/face/fingerprint/device PIN sign-in when actually supported by the Oracle Appwrite version.
2. **First encryption setup**, on a compatible trusted device, generates a random 256-bit account root and an independent emergency recovery key; requests a WebAuthn PRF-capable credential; establishes a PRF-bound recovery envelope using a reviewed KDF that combines a high-entropy credential-bound PRF result **and** the user-entered six-digit Mosaic PIN. Never store PIN, locally/verifiably hashed PIN, or any PIN-only encrypted root.
3. **Ordinary recognized device** uses its independently protected local root (after account authentication) to unlock seamlessly. The PIN is not a routine login code and is not the screen lock. Optional spaced reminders are nonblocking and must not create a locally accessible low-entropy verifier.
4. **Second device / restore:** normal account authentication and completed MFA as required, same synced passkey + platform user verification, **then the separate Mosaic six-digit PIN**. Only both factors can unwrap the cloud-stored root in the specified passive-data-theft model. A new device uses its own local wrapping key. No PIN-only restoration when passkey is lost. A wrong PIN fails authenticated envelope verification; avoid unlimited server-side PIN-only checks because there is no server-side PIN verifier. Attempt logs must not disclose PIN candidate validity or raw credential key material.
5. **Lost synced passkey:** recover with the separately backed-up high-entropy recovery key or an existing authorized device; a six-digit Mosaic PIN alone is **not sufficient**. PIN change/re-enrollment must require a trusted unlocked device or high-entropy emergency recovery, and change credential epoch atomically. Distinct enrolled credentials must each be wrapped explicitly and revocable; PRF output is per credential and does not automatically carry to a new passkey.

Why this MAY preserve secrecy for $0: a database-only attacker holding an encrypted root envelope and the six-digit PIN space lacks the independent per-passkey random PRF secret; offline PIN enumeration cannot verify guesses **without the PRF secret**. This is an application of the [W3C PRF extension](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-prf-extension) and [Bitwarden's published PRF decryption architecture](https://contributing.bitwarden.com/architecture/deep-dives/passkeys/implementations/relying-party/prf/). **This combination is an unreviewed Mosaic protocol proposal, not a cryptographic security proof.** Choose reviewed components and explicit versioning/domain separation only after design review.

**Critical residual risks:**
- A compromised or malicious passkey sync provider, authenticator, or client-supplied web script that learns PRF output can perform offline exhaustive guesses against the separate six-digit Mosaic PIN. A malicious script can also capture the entered PIN directly. This is **not equivalent** to Signal SVR3 or Meta's attested globally rate-limited PIN-only vault, which is designed to constrain recovery guesses independently of the client. It does not meet the original strong threat of a malicious app-origin operator able to replace the browser JavaScript.
- Platform provider PIN, fingerprint or Face ID verifies passkey use; it is **not substituted** for Mosaic's distinct PIN. Cross-device PRF availability is not universal. [Yubico's compatibility guide](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/Developers_Guide_to_PRF.html) identifies browser, OS and authenticator constraints. The same logical synced passkey MUST reproduce the same PRF result; Appwrite's native passkey auth endpoints alone do **not** establish PRF results are exposed.
- Passkeys must be created using a stable, audited relying-party ID. [Appwrite passkey setup](https://appwrite.io/docs/products/auth/passkeys) is available on self-hosted 2.5+, but the actual Scratch Appwrite version, RP policy, SDK/client path and availability of PRF in its WebAuthn ceremony have **not** been verified; registered credentials can prevent changing the RP ID. There is no authorization to upgrade or alter Production or the current shared Scratch Function.
- If the owner requires recovery with only **login/password + Mosaic PIN**, even after the user loses every passkey, remembered device and high-entropy emergency key, this free design **does not provide it**. No verified free Signal/Meta-equivalent protected PIN-only recovery service was found. Strong server/operator resistance for PIN-only new-device recovery remains a hard no-go until a genuine protected and rollback-resistant attempt limiter is available.
- Saved encrypted recovery envelopes alone do not make the rest of Mosaic encrypted. Older installed PWAs must be fenced from writing plaintext on the backend; private tasks, diary, categories, messages, files, settings, sharing, alerts and DR each require purpose-built encrypted contracts, migration and security acceptance.

### Minimum $0 synthetic-only proof before declaring the UX ready

- **P0 — Compatibility:** select stable Scratch RP domain, verify Oracle Appwrite version/auth policy without mutations; test one real credential creation/assertion and PRF availability; never print PRF bytes, PINs or recovery keys.
- **P1 — Two-secret proof:** create versioned AEAD-wrapped *synthetic* root using both a PRF result and a six-digit Mosaic PIN; test correct/incorrect PIN, wrong passkey, wrong owner, replay/stale envelope and no server-accessible PIN verifier. Ensure a data-only attacker cannot brute PIN without PRF, and explicitly reproduce that a party holding PRF can; no false claims.
- **P2 — Cross-device:** verify exact PRF result from one synced passkey across target iOS Safari, Android Chrome and desktop combinations. Test unavailable PRF and non-synced credentials; fallback to high-entropy recovery key. **Do not silently fall back to PIN-only encryption.**
- **P3 — UX:** new account and opt-in existing account choose and confirm their *own* six-digit PIN; separate passkey setup/check; accessible nonblocking optional PIN reminders; normal unlock without repeated PIN; new-device separate PIN recovery; failed attempts; trusted-device/emergency fallback; owner deletion and lost-key disclosures.
- **P4 — Threat review:** independently review the combination/KDF and web-origin threat, passkey provider compromise, credential revocation, browser fallback, migration/downgrade and old PWA behavior before claiming operator-blind E2EE.
- **P5 — Full app:** separately finish backend-safe per-domain encrypted sync, nonprivate sharing recipient keys, DR, client compatibility, mobile acceptance and canonical CI in isolated Scratch. Nothing above authorizes main/Production deployment or skips safety gates.

**Current verdict:** feasible **research direction with zero new infrastructure cost**, not yet verified safe in Mosaic's current environments and not the same availability/threat model as Signal or Messenger. Preserve the distinct six-digit Mosaic PIN in product design; **do not** implement a PIN-only envelope or call the existing private-Diary pilot a final product.

## 2026-11-17: $0 budget constraint and zero-cost recovery alternative (supersedes paid-infrastructure owner action below)

**Owner constraint:** absolutely no new paid infrastructure, paid provider plans or unapproved charges. Do not provision OCI E5/E6, AWS Nitro, or commission paid audits. The remaining text describes a possible paid independent-Mosaic-PIN vault for reference only.

### Recommended $0 conditional candidate: synced passkey + WebAuthn PRF

The [W3C WebAuthn PRF extension](https://www.w3.org/TR/webauthn/#prf-extension) lets a user-verified passkey supply deterministic, per-credential high-entropy output to the browser, suitable for deriving a symmetric wrapping key. [Apple iCloud Keychain](https://developer.apple.com/passkeys/) and [Google Password Manager](https://developers.google.com/identity/passkeys/supported-environments) provide passkey synchronization without charging Mosaic new infrastructure fees. Users may see their phone/device PIN, Google Password Manager PIN, biometric, or other passkey-provider verification. The PIN is verified by the device/provider and is **NOT a separately chosen six-digit Mosaic recovery PIN**. Do not claim it always has six digits.

**Key new fact:** [Appwrite released native passkeys on October 16, 2026](https://appwrite.io/changelog/entry/2026-10-16) for Appwrite Cloud and **self-hosted Appwrite 2.5+**; [official documentation](https://appwrite.io/docs/products/auth/passkeys). Existing Mosaic authentication infrastructure may be reusable. Current Oracle Scratch Appwrite version and passkey policy support are **unverified**: the connected key cannot perform project.read, and a public health/version read was inaccessible. No backend upgrades or authentication policy writes are authorized by this research.

**Appwrite passkey login does not automatically supply a WebAuthn PRF output.** The browser must request it explicitly in a WebAuthn assertion, and different browsers, operating systems, authenticator types and synced providers exhibit variable support ([compatibility research updated Sep 2026](https://www.corbado.com/blog/passkeys-prf-webauthn)). Real cross-device equality and availability must be demonstrated before relying on it for recovering a random client-generated account root. A second independent passkey is not automatically able to decrypt a root wrapped to the first.

Proposed test design: use the existing client-generated 256-bit root; derive a versioned, domain-separated wrapping key with HKDF from WebAuthn PRF output; store only an AEAD-wrapped root bound to the immutable account/project/credential and expected relying-party origin. Derive PRF only after genuine user verification. Enroll a new device by evaluating the **same synced passkey** and safely rewrapping the root with a new device key. Keep the independent high-entropy emergency recovery key (already exercised in the isolated private-Diary pilot) and previously authorized-device pairing as mandatory fallbacks. Never store a PIN verifier, a PIN-derived envelope, PRF output, or raw encryption root in Appwrite or a free provider database.

**Security limits:** A compromised Mosaic web origin, injected script or malicious browser extension may exfiltrate PRF output after a user authenticates; secure passkeys do not make arbitrary web JavaScript operator-proof. Trust also shifts to the user's passkey sync provider. Do not register passkeys until the permanent RP ID and separate Scratch/Production origin policy are chosen: Appwrite does not allow its RP ID to be changed while passkeys remain registered, and distinct Preview hosts may have incompatible RP IDs. Require an actual independent credential-PRF recovery test and fail closed if unsupported.

### $0 alternatives explicitly rejected or limited

- **Argon2/PBKDF2 encryption by a six-digit Mosaic PIN:** Rejected. An attacker with the envelope can try its one million possible values offline.
- **Cloudflare Workers / Durable Objects Free as PIN verification:** [Free storage exists](https://developers.cloudflare.com/durable-objects/platform/limits/), but this does not attest operator-immune execution, global immutable guess counts or snapshot rollback resistance. Good for ordinary application state, not proof of a protected low-entropy recovery vault.
- **OCI Always Free:** [Free A1 and AMD E2 micro shapes](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm) are NOT [SEV-SNP E5/E6 confidential VMs](https://blogs.oracle.com/cloud-infrastructure/oci-confidential-computing-on-e5-e6-shapes). No suitable free attested PIN vault was verified.
- **One-time six-digit device pairing:** May be secure when combined with an existing authorized device and reviewed encrypted key transfer, but does not recover data when all devices are lost.
- **Independent 256-bit emergency recovery key:** Available without new hardware spend and can recover without an existing device if saved; not equivalent to a six-digit PIN.

### $0 validation sequence and explicit no-go

1. Inspect the live, current dev source, current self-hosted Appwrite version and app origins without modifying the shared Scratch Function or identity policies.
2. Test actual native Appwrite passkey availability (2.5+) on a disposable Scratch origin, with stable RP ID selected BEFORE any registration. Never change Production settings.
3. Independently test browser-supported WebAuthn PRF, same-output cross-device recovery, wrong credential, absent PRF, loss of sync, invalid owner, compromised/stale ciphertext and identity boundaries. Use disposable data and no printed secrets. Include iOS and Android.
4. Add client-held wrapped-root option, high-entropy emergency recovery fallback, remembered-device operation, account switching, optional reviewed short-lived consented pairing and accessible onboarding only after passing POC tests. Native device-provider PIN verification must be clearly labeled; never claim it is a Mosaic-specific PIN.
5. Full-app encryption STILL requires server-side old-PWA plaintext-writer blocking, migration of each private domain, recipient keys for shared tasks/messages, offline/DR/erasure tests, compatible search/notifications and exact-source CI. This zero-cost path does not remove backend changes or independent security review requirements.

**Decision:** A $0 **strong-entropy, passkey-assisted recovery** design is plausible but NOT validated in Oracle Scratch; a completely independent six-digit **Mosaic-only** PIN with lost-all-devices recovery remains **NO-GO** at $0 under the original operator-resistant threat model. The UX difference needs explicit acceptance before treating this as Option A delivered. Do not claim the full encryption Preview is ready, do not spend money, and do not promote to dev/main/Production.

## Decision and non-negotiable threat model

A user-facing six-digit PIN has 1,000,000 possibilities (approximately 19.93 bits). It may authenticate retrieval of a *random client-generated recovery secret*, but must NEVER itself be used to generate, encrypt, hash, check, or unwrap that secret in a way that an Appwrite administrator, cloud operator, stolen database, client bundle, or backup can validate PIN guesses offline. Argon2, PBKDF2, peppering in a normal server, Appwrite ACLs/MFA and a cloud KMS key alone do not solve a malicious operator's unlimited guesses.

The service must enforce a small *per-recovery-credential global* failed-attempt allowance (initial design target: at most 10), with nonresettable/anti-rollback accounting across replicas, snapshots, VM replacement, retries, geographic failures, malicious partitions, administrative restores and account re-registration. After terminal lockout, the service must irreversibly deny further PIN guesses for that credential; legitimate users need a **separate high-entropy key or previously enrolled device** to re-enroll and rotate. Do not design an ordinary operator reset, audit-console bypass, allowlist exemption, or fresh account ID to reset the budget. Account identity and credential epochs must be authenticated and bound without exposing the recovery material.

The trust boundary includes user-generated client keys; independently verified hardware attestation and enclave image *measurement*; encrypted direct client-to-TEE channel; an independently trustworthy release/policy distribution mechanism; enclave-only PIN verifier/OPRF material; malicious storage snapshots; multi-instance replay; old web/PWA code; and denial of service. A source-verified client must pin approved measurements and require a nonce-bound current attestation report. The standard Mosaic/Vercel PWA JavaScript distribution remains vulnerable to an adversary able to substitute same-origin scripts, even with a secure vault: do not claim immunity from malicious web-client delivery without an additional independently validated distribution/control model.

MFA/TOTP remains separate account admission. **E2EE recovery PIN is not an Appwrite TOTP code, not a local device screen lock, and not an encryption key**. Server-side Appwrite user JWT and MFA completion alone may never reconstruct a client encryption root.

## Evidence from existing designs

1. [Signal SVR2/3 open source](https://github.com/signalapp/SecureValueRecovery2): protects low-entropy PIN recovery via strong-consensus in-memory Raft recovery attempt state; SVR3 adds secret sharing among SGX, AWS Nitro and AMD SEV-SNP hardware domains and an OPRF-based recovery interface. The maintainers prioritize secrecy over availability. Source is **AGPL-3.0**; copying/operating derivatives requires license/legal review and does not confer a managed service, turnkey Oracle deployment or audited Mosaic browser client.
2. [Signal's architectural explanation](https://signal.org/blog/secure-value-recovery/): ordinary encrypted disks and asynchronous replicas allow attacker's retry-budget rollback. Hardware enclaves *and* a trustworthy consistent, anti-rollback attempt ledger are necessary.
3. [Meta's May 2026 Backup Key Vault description](https://engineering.fb.com/2026/05/01/security/meta-strengthening-end-to-end-encrypted-backups/): an HSM fleet across datacenters with majority-consensus replication, an independently validated fleet-key distribution bundle and a public audit commitment. It is a useful security model, not an established commercially available API for Mosaic.
4. [Meta's April 2026 Labyrinth white paper, page 43](https://engineering.fb.com/wp-content/uploads/2026/05/Minos-Updates-2026-Encrypted-Backups-White-Paper.pdf): Messenger explicitly does **not** directly derive a cryptographic secret from a six-digit PIN; a Backup Key Vault authenticates release and permits up to ten incorrect guesses. Page 44 additionally distinguishes short-lived consented six-digit *device-pairing* codes (three guesses, new user approval) from persistent recovery PINs.
5. [OCI Confidential Computing](https://docs.oracle.com/en-us/iaas/Content/Compute/References/confidential_compute.htm), [Oracle's 2026 release](https://blogs.oracle.com/cloud-infrastructure/oci-confidential-computing-on-e5-e6-shapes), and [Oracle Linux remote attestation guide, updated 2026-10-07](https://docs.oracle.com/en-us/iaas/oracle-linux/oci/security-attestation.htm): VM.Standard.E5.Flex and E6.Flex expose AMD SEV-SNP and BYAS, while current Mosaic Ampere A1 does not. E6 Flex is documented for all public OCI regions; E5 Flex excludes ZRH/SIN/ORD. Supported guest images include Oracle Linux 9/10 with UEK8 and Ubuntu 24.04. OCI supplies a Veraison-based verifier, evidence collector, endorsements and remote evidence appraisal; BYAS is **a deployment responsibility**, not a pre-certified key-release protocol.
6. [AWS Nitro Enclaves](https://docs.aws.amazon.com/enclaves/latest/user/security.html), [AWS KMS attestation](https://docs.aws.amazon.com/kms/latest/developerguide/cryptographic-attestation.html): no interactive/admin access, no own storage or networking, attested PCR-based KMS release. Potential second heterogeneous platform and stronger isolation; still requires distributed attempt-counter design. AWS KMS permissions and quotas alone do not enforce a per-user immutable ten-guess budget.
7. [Azure confidential VMs](https://learn.microsoft.com/en-us/azure/confidential-computing/virtual-machine-options) / [attestation](https://learn.microsoft.com/en-us/azure/attestation/overview) and [Google Cloud confidential attestation](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/attestation-overview): viable hardware candidates, not validated Mosaic vaults.

## Candidate protocol (not approved for code)

1. Only an authenticated, *completed-MFA* Mosaic session may begin vault enrollment/recovery; do not trust a browser-supplied owner ID. An authenticated client generates a random high-entropy account encryption root, independent device wrapping keys, and an independent emergency recovery key. The six-digit PIN is never used directly as a key.
2. Client obtains nonce-bound attestation, validates hardware certificate/TCB freshness, exact reviewed vault image measurement and an independently pinned/transparent release-policy bundle. Establish an authenticated encrypted channel bound to this attestation, *not* ordinary HTTPS terminated by Appwrite.
3. Client enrolls an enclave-held recovery credential, with a zero-knowledge PAKE/OPRF or otherwise independently reviewed PIN-authentication protocol and an enclave-protected random recovery key. The server can store opaque records/metadata, never plaintext root or an offline-verifiable PIN envelope.
4. A small globally consistent guess counter is bound to a specific immutable recovery-credential epoch. Every invalid attempt atomically consumes its budget **before any response permitting another attempt**. A hostile operator cannot fork, reset, clone, restore an earlier credential state, tamper with epoch or split/quarantine a replica to mint additional attempts. Fail closed if consensus or integrity proof is unavailable. Terminal lock cannot be reset without a separately verified recovery path.
5. After successful PIN authentication and full-account access checks, the attested service releases only the wrapped/authorized recovery secret over the authenticated client-bound channel; never to Appwrite, logs, a browser-origin proxy, or an unaudited key-release path.
6. An authenticated remembered device can unlock automatically without a PIN via its nonextractable local wrapping key. New device recovery requires normal login/MFA plus PIN or a separate high-entropy recovery key (if previously saved); device-to-device pairing may use separate consented one-time codes. Lost-key state is clearly explained; lost PIN attempts cannot be silently reset by an administrator.
7. PIN change and credential re-enrollment require an independently authenticated existing device or emergency recovery key, with generation/epoch rotation and anti-rollback fencing. Rate limit across account renames, address changes, and reinstall/relogin. Recovery does not bypass app account deletion, device revocation or current privacy restrictions.
8. Reminders are optional, infrequent and dismissible, verify only against a local remembered reference where doing so adds **no offline verifier accessible to the adversary**, and never put the PIN in push/email. A reminder must not grant decryption or weaken live vault limits.
9. Design service outages as **no PIN recovery** rather than relaxed security. Existing unlocked devices should continue working offline when already provisioned. Backups/DR must preserve anti-rollback invariants or explicitly fail safe; operations must remain reversible at the deployment level without restoring an earlier attack budget.

This protocol outline needs independent formal review before adoption; it is **not** sufficient specification for implementing secure low-entropy recovery.

## Release-blocking validation gates

- **G0 — Source and scope:** reconcile current dev and isolated pilot at verified SHAs without weakening shared Function, account-isolation, diary, sync or Appwrite backend contracts; list all private domains and known plaintext/metadata exceptions.
- **G1 — Infrastructure authority:** obtain explicit paid budget/region approval; verify actual OCI tenancy shape capacity, billing rate and SEV-SNP support with a disposable **separate vault-only** instance. Existing A1/Production never becomes the vault.
- **G2 — Attestation POC:** independent relying-party verifier validates fresh AMD-signed SNP report, full certificate chain, minimum TCB, expected code/image measurement, unique nonce, channel binding, repudiation/replay and measurements updated by audited release authorization. Explicitly test wrong image, stale quote, wrong hardware, wrong TCB, MITM and fake endpoint.
- **G3 — Protection and retry budget:** no PIN-derived offline tester in any cloud storage, event log, archive, swap, snapshot or debug telemetry. Adversarial replay/fork/VM snapshot rollback/clone, restart, replica isolation, failed leader transitions, re-registration, credential version rollback, malicious admin and network partitions cannot yield more than the reviewed global guess budget. Fail closed if cannot prove.
- **G4 — Recovery semantics:** known-answer enrollment/recovery; exact MFA enforcement; owner separation; correct/incorrect PIN; irrevocable terminal lock; surviving emergency key and existing device recovery; password/account/email changes, device revocation, user deletion and DR. No silent key loss, PIN reset or downgrade to plaintext.
- **G5 — Independent assurance:** documented threat model and security proof reviewed by an external qualified cryptography/TEE specialist; third-party protocol/implementation and dependency/firmware audit; source/reproducible image or independently verified committed image; release-change transparency and browser JavaScript substitution limitations disclosed.
- **G6 — Full-app data compatibility:** all private tasks/categories/diary/photos/bucket lists/settings/messages/attachments and relevant metadata classified. Encrypted multi-user sharing needs authenticated sender/recipient keys, membership/version epochs, access revocation and safe notifications. Old PWA writers **server-side blocked** before any ordinary rows are migrated; migration resumable, reversible and verified with no data loss or operator plaintext, including offline queues and DR restore. Search/sort and social projections must be redesigned or explicitly bounded.
- **G7 — UX and quality:** first-time account flow, existing-account opt-in/resume, normal remembered-device unlock, recoverable new-device flow with six-digit PIN, alternative emergency key/device pairing, optional PIN reminder, rate/lockout education, back button and error states; no standalone pilot URL or manual refresh. Test real browser/phone and full canonical CI on exact reviewed source and Scratch deployment. No Production promotion without separate authorization.

**Go/no-go:** G1 through G5 are currently **unverified/failed by absence of evidence**. G6 and G7 are not implemented outside the isolated Diary pilot. A full E2EE/6-digit PIN Preview would misrepresent these guarantees and must remain blocked. A new isolated attestation-only experimental Preview is permissible only after G1 budget/tenancy approval, and must use synthetic keys without personal data.
