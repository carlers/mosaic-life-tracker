# Juicebox PIN recovery: source-level feasibility and security audit for Mosaic

**Date:** 2026-11-18. **Status:** research and static source review; **NOT approved or deployed**. **Issue:** [#1662](https://github.com/carlers/mosaic-life-tracker/issues/1662). **Budget:** strictly $0 new spend, with no trial or billing commitments. **Priority:** optional new-device recovery using a distinct user-chosen **six-digit Mosaic PIN**, while normal account authentication and existing-device key availability remain separate. Passkeys and biometrics are deferred.

**Executive conclusion:** Juicebox is a plausible established *cryptographic protocol* for exactly this recovery UX, not a turnkey permanently-free, independently administered recovery *service*. Its paper, MIT client SDK, and AGPL Go software realm are publicly inspectable. Static audit found a **candidate missing-update acknowledgement in the MongoDB attempt-counter persistence path** and a **configuration validation mismatch** in the latest SDK. Neither was reproduced at runtime here; neither should be classified as a confirmed exploited vulnerability. Other unresolved production gates include malicious storage rollback, independently operated recovery realms, whole-system upgrade and deletion guarantees, user recovery after realm loss, PWA source substitution, source maintenance, browser/WASM compatibility, and zero-cost hosting longevity. **NO-GO for actual users or production PIN-only recovery at this checkpoint.** **GO for an isolated, fully synthetic three-realm lab with no cloud charge, subject to access to the source and test dependencies.**

## 1. What Juicebox actually provides

1. **Enrollment:** Browser generates a high-entropy random account root for Mosaic, then registers that 32-byte value as an arbitrary Juicebox secret. Juicebox's SDK derives a PIN-dependent access value using a KDF, distributes threshold OPRF private shares and shares of the key-wrapping scalar among distinct configured realms, and stores authenticated encrypted secret data. Each realm retains a realm-specific PIN-verification tag, a version, a recovery policy and its own counter. The single realm record does **not** disclose the complete root, but if a full threshold of realm records/OPRF secrets is compromised the small PIN space may be attacked offline.
2. **Normal account login:** Mosaic's Appwrite password/MFA session does **not itself decrypt the key**. An appropriately server-issued realm JWT (immutable owner-bound sub, realm-bound aud, expiry, issuer/kid) authorizes protocol operations. A maliciously authenticated session can make recovery guesses and cause DoS even without learning the secret.
3. **New-device recovery:** The newly authenticated client submits a PIN-dependent **blinded** OPRF request to a threshold of realms; each tracks guesses and answers with its authenticated share. Client checks threshold agreement, proofs, PIN commitments and server shares. On successful recovery the client reconstructs the **random Mosaic encryption root locally**; Appwrite and individual realms should not receive the root or the plaintext PIN. Client can then rewrap the root under its own local device-specific key and decrypt Mosaic's stored ciphertext.
4. **Terminal lockout and lifecycle:** A realm moves its registration to NoGuesses after exhaustion and drops the old registered data. A valid PIN proof resets its attempt counter. Registration can overwrite previous credential state, and deletion can occur after account authentication without the old PIN, by design. Secure account recovery must distinguish "can sign in" from "can still recover encryption" and explain irreversible loss. An independent high-entropy emergency recovery key remains prudent.
5. **Per-realm limitation:** Each realm maintains **its own** guess count. If threshold T of N allows alternate realm subsets, total online guesses can exceed an apparent per-realm budget even without rollback. For illustrative 2-of-3 quorum, pair AB can consume five attempts, AC five, BC five: each realm participates ten times, while attacker obtains fifteen pair-level attempts. This is a mathematical scenario, **not an exploit verified against Juicebox's full client state machine**. A strict 3-of-3 requires every realm each time and gives no recovery if even one is offline.

Sources: [protocol PDF](https://eprint.iacr.org/2025/348.pdf), [software realm README](https://github.com/juicebox-systems/juicebox-software-realm), [Matthew Green's analysis](https://blog.cryptographyengineering.com/2025/06/09/a-bit-more-on-twitter-xs-new-encrypted-messaging/).

## 2. Direct software realm implementation findings

### S1. Potential recovery counter persistence failure under concurrent MongoDB updates — **HIGH priority to reproduce**, unconfirmed runtime

Source: [records/mongoStore.go at fixed SHA](https://github.com/juicebox-systems/juicebox-software-realm/blob/2e485aac584a6c9ada1fb9f156dc4d7cad3ab338/records/mongoStore.go), method MongoRecordStore.WriteRecord.

The code reads an existing version, then calls collection.UpdateOne with filter {_id, version: previousVersion} and SetUpsert(previousVersion == nil). It checks only the **err** return and **discards UpdateResult**. The standard MongoDB Go driver documents that an UpdateOne with no matching record is a non-error result with MatchedCount=0. If two Recover2 calls read the same version concurrently, one successful write increments the stored GuessCount and version, while the second can have MatchedCount=0, report **nil error**, and still return its valid OPRF response from the router. This suggests a plausible avenue for more recovery responses than recorded guesses on the Mongo backend.

This is a **static-code hypothesis** supported by API contract and handler flow, **not experimentally demonstrated**, and actual exploitability depends on concurrency, request scheduling, JWT eligibility and SDK verification. An appropriate fix would require checking matched/upserted outcome and failing closed/retrying on mismatch; a focused concurrent recovery test and independent security review must confirm. Do not use unmodified Mongo provider for protected low-entropy PIN deployment. **Do not publish detailed operational exploit instructions or assume every Juicebox storage backend shares this issue.**

### S2. DynamoDB and Bigtable conditional writes are more explicit — not rollback proof

[records/dynamoDbStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/2e485aac584a6c9ada1fb9f156dc4d7cad3ab338/records/dynamoDbStore.go) uses version-conditional PutItem (failed condition returns an error). [records/bigtableStore.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/2e485aac584a6c9ada1fb9f156dc4d7cad3ab338/records/bigtableStore.go) uses a conditional mutation and explicitly rejects unexpected conditionalResult. Both protect against normal concurrent lost updates **but do not prevent an administrator who owns storage from restoring a prior snapshot**. MemoryRecordStore is in-memory only and loses all state and counts after restart; never use it as a production vault.

### S3. Realm registration/lockout/account security depends on externally issued tenant JWT

[router/router.go](https://github.com/juicebox-systems/juicebox-software-realm/blob/2e485aac584a6c9ada1fb9f156dc4d7cad3ab338/router/router.go) validates JWT identity and derives a tenant/user record. Register2 replaces a record and resets the count to zero; Recover2 increments before serving an OPRF response; Recover3 validates an unlock tag and resets counts on success; Delete marks NotRegistered. A compromised Mosaic JWT issuer with users' identities can deny users access by deleting or overwriting records, even when it cannot obtain the recovered root. [Maintainer's explanation](https://github.com/juicebox-systems/juicebox-software-realm/issues/1#issuecomment-3233110747) explicitly calls this out. 

For Mosaic, allow the user to enter recovery only after the exact fully MFA-completed account session. Authorize operations using a protected issuer, immutable owner identifier and **per-realm aud**; treat all registration/deletion/rotation as high-risk, logged, explicitly confirmed operations. Separate low-privilege recovery JWT issuance from higher-assurance key mutation where possible **without** silently modifying the published protocol. Be aware the operator controlling all JWT signing keys can cause DoS; no ordinary claim that the PIN itself protects registration/deletion.

### S4. SDK registration-threshold validation mismatch — **availability bug candidate**, unconfirmed runtime

Source: [rust/sdk/src/configuration.rs at fixed SHA](https://github.com/juicebox-systems/juicebox-sdk/blob/2e0f544e3fd0bd0997a034f73c8efb6fade3690c/rust/sdk/src/configuration.rs). The documentation says register_threshold must be >= recover_threshold. The executable assertion with the message "register_threshold must be at least recover_threshold" instead checks **recover_threshold <= realm_count** again, which is already enforced, and never compares register_threshold >= recover_threshold. This appears to allow a misconfigured registration threshold smaller than the recovery threshold, potentially declaring enrollment ready with insufficient available shares. Pin configuration validation in Mosaic and add a regression test; don't classify as a live user data-loss incident without reproducing.

### S5. PIN hardening and 2019 parameters need current evaluation

[SDK rust/sdk/src/pin.rs at fixed SHA](https://github.com/juicebox-systems/juicebox-sdk/blob/2e0f544e3fd0bd0997a034f73c8efb6fade3690c/rust/sdk/src/pin.rs) exposes Standard2019 and **FastInsecure (test only)**. Standard2019 uses Argon2id with m_cost=1024*16 KiB, i.e. **16 MiB** of memory, t_cost=32 and p_cost=1. The paper's prose labels "16 KiB" memory; actual source units and modern device performance must be checked before specifying production policy. FastInsecure must never be enabled for users. Argon2 slows a stolen-threshold attack but does **not** turn one million possible six-digit PINs into high-entropy secrets. Any future parameter changes require safe versioned re-registration compatible with existing accounts.

### S6. JavaScript browser/PWA integration is *not* verified

The [official JavaScript README](https://github.com/juicebox-systems/juicebox-sdk/blob/2e0f544e3fd0bd0997a034f73c8efb6fade3690c/javascript/README.md) imports Client, Configuration, Realm and PinHashingMode, and uses register, recover, delete and server-provided realm JWTs. The package includes a Rust/WASM binding; Mosaic is a React/Vite PWA with strict initial/Home closure size gates. Browser compatibility, iOS WebKit memory constraints, offline behavior, service-worker updates, WASM bundle size, CSP/SRI compatibility, cryptographically secure randomness, own-origin XSS/source substitution and key cache removal are **unmeasured**. Do not simply add an unreviewed npm package to the live app before a separate disposable build and actual browser testing.

### S7. Maintenance, licenses and review

- SDK repository **MIT**; Go software realm **AGPL-3.0**; HSM realm **AGPL-3.0**. Modified hosted Go code raises AGPL network-source obligations; independent legal review of distributing/operating modified code is advisable.
- Verified software Go head date **2024-08-14**; HSM repo head **2024-08-15**; SDK head **2026-08-01** (0.3.7). These exact dates only describe the discovered GitHub heads, not support guarantees.
- [Upstream issue #4](https://github.com/juicebox-systems/juicebox-sdk/issues/4#issuecomment-6113024258) includes a project contributor saying the startup failed to attract sufficient customers, that no fundamental design flaw was known to them and that the software is abandoned *as far as they knew*. This is not a guarantee no third party maintains forks, and a 2026 SDK update exists. The original Go server's security patch ownership is **not established**.
- [Upstream open Mongo PubSub issue](https://github.com/juicebox-systems/juicebox-software-realm/issues/2) independently reports a typed-nil error handling problem that can lead to panic; its existence is another reason to audit Mongo reliability, not proof of this report's separate CAS suspicion. [Upstream SDK issues](https://github.com/juicebox-systems/juicebox-sdk/issues) also include platform crash/dependency-maintenance concerns.
- X's published [Trail of Bits review link](https://github.com/trailofbits/publications/blob/master/reviews/2025-10-x-xchat-securityreview.pdf) was located, **but the audit PDF's full contents/scope were not read** in this review. Thus **no claim that ToB audited or approved the Go software realm** is made.
- The [HSM realm README](https://github.com/juicebox-systems/juicebox-hsm-realm) explicitly says its commodity-hardware software HSM is for testing, not equivalent hardware security. The real HSM implementation requires Entrust devices, authenticated consensus, Google Bigtable, Pub/Sub and Secret Manager. Oracle **Always Free Vault Encrypt/Decrypt** cannot execute this programmable realm code as a drop-in.

## 3. What a $0 deployment actually requires

| Configuration | New cash spend | Trust properties | Recommendation |
|---|---|---|---|
| Three in-memory local realms on one research machine | $0 | Basic functional behavior only; one owner and restart wipes counter/key state | **GO for isolated synthetic laboratory only** |
| Three software realms on Mosaic's own existing OCI infrastructure | Could be $0 compute within allowance | A single host/administrator may copy enough OPRF shares, restore counters or alter code. Realms NOT independent | **NO-GO for operator-blind claims** |
| Three separate free-tier VMs all under Mosaic's own owner credentials | Might have $0 billed within quotas, but no guarantees | Vendor separation is not administrative independence; one owner can control all | **NO-GO for original threat model** |
| Three independently administered free software realms, e.g. recovery guardians | Potentially $0 Mosaic cash if other groups volunteer reliable services | Threshold of genuinely independent operators must remain honest, available and protect snapshots | **Research conditional**; no identified commitments, uptime, audit or production guarantees |
| OCI Free HSM plus two self-operated software realms | Unverified remaining OCI free key quota | HSM master key is nonexportable but authorized Decrypt calls still operate under Mosaic IAM. Not a programmable HSM realm, thus no proven immutable PIN counter | **NO-GO as direct Juicebox HSM replacement** |
| Actual Juicebox Entrust HSM-backed realms or attested alternatives | No perpetual free turnkey infrastructure found | Could satisfy stronger counter rollback protections when properly audited/attested | **Out of scope** under $0 budget |

**The hard requirement is not three machines; it is independent authority over protected key shares and immutable security policy.** A 2-of-3 software arrangement is only operator-resistant if no single operator controls two shares and the honest operators actually preserve live counters. Availability (one offline), confidentiality (compromise of threshold) and exactly bounded PIN attempts cannot all be assumed simultaneously. More realms also mean more administrations to coordinate, persistent state to back up, monitoring, legitimate deletion/erasure, emergency recovery and protocol upgrades.

### Threshold / attempt-budget decision

- For a simple **3-of-3** configuration every realm participates; fewer combinations to amplify guesses, but the permanent or temporary loss of a single realm blocks recovery. This is unacceptable as the **only** backup path without an independent high-entropy emergency key.
- **2-of-3** tolerates one outage but permits alternate quorum subsets; a per-realm ten-guess policy does not necessarily mean ten total attempts for a user. It must be adversarially modeled and tested with the actual SDK.
- If a realm operator can roll back their storage or reveal their OPRF share, low-entropy PIN protection degrades. Even two genuinely independent guardians need explicit mutual noncollusion and service-sustainability assumptions; formal academic design is not a production audit.
- The server/Mosaic issuer can mint JWTs on behalf of accounts. With honest independent realms and uncompromised PIN, a stolen account cannot directly obtain plaintext root, but malicious issuer can force exhaustion or overwrite/delete credentials. Define recovery loss UX, emergency backup and revocation.
- PWA JavaScript delivered by a malicious Mosaic operator can exfiltrate PIN/root during user unlock even with independent realms. The original promise of protection against arbitrary malicious web code delivery requires separate mitigations/disclosure, not simply more recovery realms.

## 5. Recommended decision

**Recommendation A (now, $0):** Perform a synthetic-only, disposable three-realm lab using the **existing unmodified** upstream SDK and Go server, then reproduce and evaluate the candidate Mongo counter acknowledgement mismatch and SDK configuration validation defect. No use of real keys, no access to Production, no paid services. If a source issue is confirmed, plan responsible upstream disclosure and scoped patch/security tests before any Mosaic integration.

**Recommendation B (parallel research):** Identify at least two **genuinely independent, reliable free operators** prepared to run persistent realms under separate keys/administrators and accept long-term operations and account erasure. Without that evidence, do not depict software-only threshold recovery as resisting the Mosaic operator. Reassess off-the-shelf HSM-grade services only if a truly free and independently attested API becomes available.

**Recommendation C (product sequencing):** Implement E2EE independently of PIN-only recovery using client-generated account roots and a strong emergency recovery key or authorized-device transfer. This does **not** require approving the above research realms. If owner insists on six-digit-only recovery, block shipping that flow until suitable protected recovery service is validated. Keep everyday device unlock and password login distinct from encrypted account recovery; no biometric/passkey work now.
