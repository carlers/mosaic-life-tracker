# Disposable real GoTrue data recovery lab (#1027)

The **Supabase Real GoTrue Restore Lab** runs only on a temporary GitHub Actions runner, using Supabase CLI 2.81.3, the actual local GoTrue + PostgREST services, locally generated password accounts and a newly generated age encryption identity. Its shell refuses execution outside GitHub Actions or with a hosted access token / DATABASE_URL environment variable. No hosted project, private Fedora archive/key, Vercel secret, Appwrite user, SMTP email, OAuth or Production data is used.

The test creates one genuine GoTrue email/password owner and signed category/task rows, acquires core writer authority, encrypts a custom-format PostgreSQL archive, fully decrypts and compares archive bytes, and checks the read-only TOC inventory. It resets the local Supabase stack to a **freshly initialized empty schema**, then uses pg_restore only for six allowlisted **data** objects: auth.users, auth.identities, the core authorities ledger and owner revisions, categories and tasks. It does NOT copy managed Supabase schema definitions or Auth sessions / refresh-token tables. App-controlled insert triggers are disabled only during that test's data rehydration and reenabled afterward.

Acceptance requires the original password to sign in again to the recovered Auth account, canonical owner ID to remain the same, persisted task/category revisions to be readable, pre-restore session authority to be refused, and an independently registered second signed account to be unable to read or write the first owner's data. Synthetic plaintext backup files and credentials exist only on the transient test runner and are cleaned up on completion.

**Limitations:** This exercises reset-and-restore on the **same local Supabase stack/schema version**. It is NOT a separate machine/managed-platform restore, and does not prove compatibility with the user's real PostgreSQL 17 hosted snapshot, current live Auth providers, service configuration, old installed PWAs, Storage, SMTP, email confirmation policy or real user records. A migrated installation will require freshly configured JWT/Auth settings and forced reauthentication. No hosted schema, user, Auth policy or signup setting may be changed solely on the strength of this lab.

The owner's private Fedora age snapshot must remain private and must be separately restored into a disposable *initialized* Supabase target with signed two-owner tests before accepting live recovery or a public release.
